Mixture-of-LoRA, built and watched

One LoRA teaches a frozen model one new skill for a few megabytes. Real systems need many at once. This is how the field composes them — with a working X-LoRA build where you can watch a learned gate route each token to the right expert.

1 · The problem, from first principles

Begin with what you actually want: one model that does many different things well. The obvious route — fine-tune the whole model on all of them together — quietly fails, and the reason is worth sitting with. The tasks fight. Teaching the same weights to do arithmetic and to reformat text and to follow a rigid schema pulls each weight in competing directions; the shared parameters settle on an average that serves no task cleanly. That averaging-away of conflict is interference — the single enemy this whole field is organized against.

LoRA (Low-Rank Adaptation) is the move that defuses it. Freeze the giant model, and store each new skill as a tiny low-rank delta — a few megabytes — that nudges the frozen weights toward one task. Because each skill now lives in its own small module instead of in the shared weights, skills no longer have to fight for the same parameters. You can keep hundreds on a shelf and snap any one on. (What is that low-rank delta, exactly — why does rank-8 carry a whole skill, and how is it free at inference? That's its own deep-dive: what a LoRA actually is, from the weights up, measured on a real fine-tune.)

But that victory just relocates the hard question. If every skill is a separate part, you now have to hold many at once and decide, for each input, how much of each to use — without letting the interference you escaped creep back in through the way you combine them. That is the entire problem, and it has one clean shape:

The reframing that unlocks everything. Once every skill is a low-rank delta on a shared base, skills become composable objects — things you can add, weight, and switch on and off. Mixture-of-LoRA is simply Mixture-of-Experts where the experts are cheap swappable adapters instead of whole network blocks. Every method is one answer to "how do you arbitrate between them" — and they fall into three families.

2 · Three families (getting the category right is the whole game)

FamilyWhat it doesTools
Merge / composefold several trained LoRAs into one, oncePEFT add_weighted_adapter, LoRAHub, mergekit
Routed MoE (learned gate)a trained router picks/blends experts per token at run timeX-LoRA, MixLoRA, MoLE, MOELoRA
Serve many LoRAshost thousands of adapters on one base; caller names which per requestLoRAX, vLLM, S-LoRA, Punica

These three aren't arbitrary — they're separated by one question: when is the "how much of each" decision made? Merge decides it once, offline and bakes in a fixed blend — nothing extra to run later, but it can't adapt to the input. Routing decides every time, at inference — adaptive per token, but you pay to run a gate. Serving doesn't blend at all — it hands one whole adapter to each request. Only the middle family is the "mixture" concept proper — a gate that actually decides. We build it with X-LoRA: the best-maintained routed option (it lives inside Hugging Face PEFT), a true per-token learned gate, small enough for one GPU.

3 · How X-LoRA actually works

X-LoRA turns a set of already-trained, frozen LoRA experts into a token-adaptive mixture by adding one small trained thing — a scalings classifier (a little MLP). Three steps, but each answers a real question:

  1. First pass — read the meaning. Run the base model once to get its hidden states: the model's own internal read of the input. This is the crux, and it's why routing on the raw text wouldn't do. The token "42" means one thing after "what is 40 + 2" and something else inside a phone number — same spelling, different skill needed. The hidden state carries that context, so the gate can decide on meaning rather than surface form.
  2. Classify — which skill does this token need? The classifier reads those hidden states and emits a weight for every expert, at every token, at every layer — shape (batch, seq, n_layers, n_experts), softmaxed over experts. Strip away the machinery and it is just a learned classifier of "what kind of token is this, and which skill should handle it."
  3. Second pass — act on it. Run the model again for real, scaling each expert's contribution by those weights.

Why two passes? A chicken-and-egg forces it: to route on the model's understanding you must already have that understanding — but the model's output depends on which experts you fire. X-LoRA breaks the loop by taking one clean, expert-free read first, deciding from that, then applying. The price is literal and worth naming: the base model runs twice per token. That is the honest, unavoidable cost of routing on meaning instead of on the prompt string.

Why a dense softmax over all experts, instead of picking one? Because a soft blend can never lose a skill — every expert stays available, if only faintly, so at a boundary the model can lean on two at once. The price is decisiveness: the blend comes out gentle (we'll measure exactly how gentle), which is precisely the knob the variants section turns.

The fundamental point. X-LoRA adds intelligence about a set of frozen skills without touching the skills themselves — only the gate learns. It routes on the model's internal state, per token and per layer, because the right skill for a token is a fact about its meaning, and meaning is exactly what a hidden state holds. Everything downstream — soft vs sharp, dense vs sparse — is a knob on how strongly to act on that judgment.

Real-library gotchas (peft 0.13/0.20): base must have use_cache=False; name the adapters "0","1","2" (peft loads them under integer names but activates them under your config's dict keys → else KeyError on first forward); and .generate() fights the double forward, so decode greedily by hand — one plain forward per token.

4 · The build

To see routing you need experts that behave visibly differently — so on a frozen Qwen2.5-0.5B-Instruct we trained three deliberately distinct skills: math (arithmetic), shout (uppercase transform), json (structured output). The distinctness is deliberate: if the experts overlapped, a perfectly correct router would be indistinguishable from a confused one — you couldn't tell routing from noise. Then we wired all three under X-LoRA and trained only the gate, base and experts frozen. That isolation is what makes the result readable: anything the model gains can only be routing, never new skill. ~10 minutes on one L4.

6 · Sharpening the gate — variants

Our baseline gate routed correctly but softly. The fix is a gate config change, not new training data. We re-ran the same experts under three gates and measured two things: mean max-weight (how decisive each token's routing is, 0.33 = a three-way tie) and task-match (how often the top expert matches the prompt's task).

GateWhat changesMean max-weightTask-match
dense-t1.0dense softmax, temp 1.0 (baseline)0.3635%
dense-t0.3dense softmax, temp 0.3 (colder)0.3653%
sparse-top1sparse top-1 (hard MoE)0.4565%

What we actually measured is more interesting than the folklore. Lowering the softmax temperature (τ 1.0 → 0.3) barely sharpened the blend (max-weight 0.36 → 0.36) — because this gate's raw per-expert logits ended up close together, so even a cold softmax stays soft — but it did fix which expert wins more often (task-match 35% → 53%). The decisive lever was sparse top-1 routing: forcing the gate to pick a single expert per token and ignore the rest — a hard Mixture-of-Experts — jumped both numbers (max-weight 0.45, task-match 65%). Here is that sharpest config (sparse-top1) on the same prompts — the bars are now far more committed:

The tradeoff, made concrete. Temperature only re-weights a blend the gate already leans; sparse top-k is what actually commits — and it's the only option that also saves compute, since the unpicked experts are never applied. The cost of committing: it's brittle when a token genuinely needs two skills at once (our JSON case stays weak throughout — the base already emits JSON, so no expert earns the gate's confidence). Sharper isn't universally better; it's better exactly when the tasks are truly distinct.

7 · MixLoRA — grow experts, don't compose them

X-LoRA takes experts you already trained and adds a gate on top. MixLoRA asks the opposite question: what if the experts and the router are born together? It inserts several small LoRA experts inside every feed-forward block and trains them jointly with a per-token top-k router — a true sparse Mixture-of-Experts, where only the chosen few experts run for each token.

X-LoRA (compose)MixLoRA (grow)
Expertspre-trained separately, frozen, named (this is the math one)born inside the FFN, trained from scratch, anonymous
What trainsonly the gate (experts frozen)experts and router, jointly
Routingdense blend over all experts (per token/layer)sparse top-k — only k experts fire → saves compute
Specializationassigned by youemerges from the router + a load-balance loss

Why does specialization emerge if nobody assigns it? A feedback loop. Early on the router sends each token type to whichever expert happens to handle it slightly better; that expert then trains a little more on those tokens and gets better still, so the router sends it even more of them. Co-adaptation turns a tiny initial edge into a committed specialist — no labels required. The danger is the same loop running away: one expert eats everything and the rest die (the "rich get richer" collapse). That is exactly what the load-balancing auxiliary loss is for — it gently penalizes lopsided routing so several experts stay alive long enough to find distinct niches.

We built it from the real mixlora modules (its MixLoraSparseMoe router + LoRA experts) with a hand-written training loop, on the same frozen Qwen2.5-0.5B and the same math/shout/json data — 4 experts, top-2 routing, experts+routers trained together with that load-balance loss. Then we read out, for each task, which anonymous expert its tokens flowed to:

Specialization emerged on its own. Nobody labeled the experts, yet expert 3 became the math expert (58% of math tokens) and expert 1 the shout expert (44%) — purely from the router learning to send similar tokens to the same place. Two honest wrinkles the numbers expose: expert 0 nearly died (≤12% everywhere — the classic MoE failure the load-balance loss fights but doesn't fully cure at this scale), and JSON never found an owner (spread ~evenly) — the same signal X-LoRA gave us: the base already emits JSON, so no expert needs to own it. Emergent specialization is real, but it is lumpy, not clean.

8 · Rank-as-expert — the third philosophy

X-LoRA makes each whole adapter an expert; MixLoRA grows experts inside the FFN. A third camp (FlyLoRA, Single-Ranked MoE) asks: why not go smaller still? A LoRA update is already a sum of 8 rank-1 pieces — ΔW·x = Σᵢ Bᵢ(Aᵢ·x). Make each rank an expert, and add a tiny router that decides, per token, which ranks fire.

We built it directly (no library) on the same frozen Qwen2.5-0.5B and data: one small LoRA on the attention projections with 8 ranks, a per-token router picking the top-2 ranks, trained with a load-balance loss. Then we read out which ranks each task's tokens used:

math0.000.000.500.170.000.080.000.25
shout0.060.000.120.000.750.000.000.06
json0.100.000.000.100.720.000.000.07
Specialization at the finest grain — and it's the sharpest of the three. Individual ranks pulled apart cleanly: rank 2 became the math rank (50% of math tokens) and rank 4 the format rank (75% of shout, 72% of json). Two honest reads of that: the routing is crisper than the whole-FFN experts (a rank is a narrow thing, easy to commit to), and shout and json ended up sharing rank 4 — the router discovered they're the same kind of task (impose a surface format) and reused one rank for both, while three ranks went nearly unused. This is the most parameter-thrifty answer on the whole map: no extra expert copies at all, just a gate over the ranks a LoRA already has — trading raw capacity for near-zero overhead. Three builds, three answers to one question: an expert can be a whole adapter, a sub-network, or a single rank.

9 · Where this sits

Combine skills once, cheaply → merge (PEFT/mergekit). Serve thousands of task adapters → LoRAX/vLLM. Have the model decide, per token, which skill to use → routed mixture-of-LoRA, and X-LoRA is the cleanest way to hold it in your hands. And these three builds are just three points in a much larger field — see the mixture-of-LoRA design space: 16 methods read from first principles and placed on four axes.
