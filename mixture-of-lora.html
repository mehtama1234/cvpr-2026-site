Mixture-of-LoRA, built and watched

One LoRA teaches a frozen model one new skill for a few megabytes. Real systems need many at once. This is how the field composes them — with a working X-LoRA build where you can watch a learned gate route each token to the right expert.

1 · The problem, from first principles

A large model is expensive to train and huge to store. LoRA (Low-Rank Adaptation) made specialization cheap: freeze the giant model, and learn a tiny low-rank delta — a few MB — that nudges it toward one task, style, or domain. You can keep hundreds of these adapters on disk and snap any one onto the base.

But one adapter is one skill. Real use wants many at once — math and a format and a domain — and a single LoRA can't hold conflicting skills without blurring them. So the real question: once a skill is a small, swappable part, how do you combine many parts intelligently?

The fundamental reframing. Once every skill is a low-rank delta on a shared base, skills become composable objects. Mixture-of-LoRA is just Mixture-of-Experts, where the experts are cheap swappable adapters instead of whole network blocks. That splits into three families of tools.

2 · Three families (getting the category right is the whole game)

FamilyWhat it doesTools
Merge / composefold several trained LoRAs into one, oncePEFT add_weighted_adapter, LoRAHub, mergekit

Only the middle family is the "mixture" concept proper — a gate that decides. We build it with X-LoRA: the best-maintained routed option (it lives inside Hugging Face PEFT), a true per-token learned gate, small enough for one GPU.

3 · How X-LoRA actually works

X-LoRA turns a set of already-trained, frozen LoRA experts into a token-adaptive mixture by adding one small trained thing — a scalings classifier (a little MLP):

  1. A first forward pass runs the base model to read its hidden states — what it currently understands about the input.
  2. The classifier reads those hidden states and emits weights of shape (batch, seq, n_layers, n_experts), softmaxed over experts — a weight for every token and every layer.
  3. A second forward pass runs for real, scaling each expert's contribution by those weights.
The fundamental point. The gate routes not on the surface prompt but on the model's own internal state, per token, per layer. Only the gate trains; experts and base stay frozen. The price is literal: the base runs twice per step — the honest cost of dynamic routing.

Real-library gotchas (peft 0.13/0.20): base must have use_cache=False; name the adapters "0","1","2" (peft loads them under integer names but activates them under your config's dict keys → else KeyError on first forward); and .generate() fights the double forward, so decode greedily by hand — one plain forward per token.

4 · The build

On a frozen Qwen2.5-0.5B-Instruct we trained three deliberately distinct experts so routing would be visible: math (arithmetic), shout (uppercase transform), json (structured output). Then we wired all three under X-LoRA and trained only the gate on a mixed dataset — base and experts frozen. ~10 minutes on one L4.

That leads straight to the question of how to sharpen it.

6 · Sharpening the gate — variants

Our baseline gate routed correctly but softly. The fix is a gate config change, not new training data. We re-ran the same experts under three gates and measured two things: mean max-weight (how decisive each token's routing is, 0.33 = a three-way tie) and task-match (how often the top expert matches the prompt's task).

GateWhat changesMean max-weightTask-match
dense-t1.0dense softmax, temp 1.0 (baseline)0.3635%
dense-t0.3dense softmax, temp 0.3 (colder)0.3653%
sparse-top1sparse top-1 (hard MoE)0.4565%

What we actually measured is more interesting than the folklore. Lowering the softmax temperature (τ 1.0 → 0.3) barely sharpened the blend (max-weight 0.36 → 0.36) — because this gate's raw per-expert logits ended up close together, so even a cold softmax stays soft — but it did fix which expert wins more often (task-match 35% → 53%). The decisive lever was sparse top-1 routing: forcing the gate to pick a single expert per token and ignore the rest — a hard Mixture-of-Experts — jumped both numbers (max-weight 0.45, task-match 65%). The tradeoff, made concrete. Temperature only re-weights a blend the gate already leans; sparse top-k is what actually commits — and it's the only option that also saves compute, since the unpicked experts are never applied. The cost of committing: it's brittle when a token genuinely needs two skills at once (our JSON case stays weak throughout — the base already emits JSON, so no expert earns the gate's confidence). Sharper isn't universally better; it's better exactly when the tasks are truly distinct.

7 · Where this sits

Combine skills once, cheaply → merge (PEFT/mergekit). Serve thousands of task adapters → LoRAX/vLLM. Have the model decide, per token, which skill to use → routed mixture-of-LoRA, and X-LoRA is the cleanest way to hold it in your hands.
