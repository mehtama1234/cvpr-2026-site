Reinforcement Learning — why it works, mathematically

Teach an agent to play a game or steer a robot when you cannot tell it the right move — you can only let it try and hand it a score afterward. How do you improve when you can grade outcomes but never the moves themselves?

Plain-English big picture

What this is really about

Reinforcement learning trains from consequences. The model tries an action, receives a reward or penalty, and shifts probability toward actions that beat expectation.

Where topology and shape enter

Topology appears in the space of possible states and actions. A robot or game agent moves through a connected landscape of choices. Good learning respects which states can reach which other states.

Where the same idea appears elsewhere

RL appears in robotics, games, dialogue, recommender systems, control, resource allocation, and model alignment.

Why Reinforcement Learning is worth learning

It matters because many tasks cannot be learned by copying examples alone. Some require trying actions and learning from what happens.

The key turn — the principle at work

The stuck point. In many tasks, the right action is not the one with the best immediate result. Reward can arrive late, after many choices.

The mathematical move. The principle is optimizing expected future return. Reinforcement learning assigns credit across time: actions are judged by the rewards they lead to, not only by what happens now.

What changes. Learning stops needing a correct action label at every step. The agent can learn from outcomes. The hard part is credit assignment: deciding which earlier choices caused the later result.

The problem, as a quantity

An agent takes actions and the world hands back a reward — points, a win, a job done. Nobody ever tells it what the right action was; it only sees how well things turned out. Worse, the reward comes from the world, so there is no smooth path leading from 'the reward I got' back to 'how I chose my action' that you could follow to improve.

So the problem is to get better using only a score on the outcome, never a correction on the move. And once you can do that, a second problem appears that is arguably harder: the agent will climb exactly the score you wrote down, whether or not that score truly captures what you wanted — so writing a reward that means what you intend becomes the real battleground.

The core ideas — and why they work

You cannot grade the moves, so nudge the odds of the ones that paid off

∇_θ J(θ) = E[ ∇_θ log π_θ(a_t|s_t) · (R_t − b) ]
Here is the bind. The agent picks moves, the world hands back a reward, but nobody ever says what the right move was — and because the reward comes from the world, you cannot trace a smooth slope from 'reward' back to 'how I chose.'

The way out is indirect. Do not try to improve the reward directly; instead adjust the odds with which the agent picks each move. Run an episode, see the total reward, and then shift the agent's move-picking so that whatever it did on a well-rewarded episode becomes more likely, and whatever it did on a poorly-rewarded one becomes less likely. You can take a smooth slope of 'how likely was this move,' even though you cannot of 'how good was the reward' — so learning flows through the choice the agent controls, rather than through the world it does not.

Judge each outcome against what was normal, not against zero

Subtract b from the return: (R_t − b) where b ≈ V(s_t), the expected return from this state
There is a problem with 'just make rewarded moves more likely.' If every reward is positive, then every move gets encouraged, only by differing amounts, and the useful signal drowns in noise.

The fix is to compare each outcome to what you would normally expect from that situation, and react only to the difference. Scored 100 when you usually score 90? That move did better than normal — encourage it. Scored 100 when you usually score 110? Worse than normal — discourage it, even though 100 is a positive reward. Subtracting the 'normal' level turns raw rewards into 'better or worse than expected,' which points the learning far more sharply and makes it far steadier. The agent learns from surprise, not from the mere sign of the number.

The agent optimizes exactly what you wrote, not what you meant

The gradient points uphill on r — and every slope, no matter how unintended, is a valid hill to climb
Here is the dangerous edge. The agent relentlessly makes whatever scored well more likely — it climbs the reward you actually wrote down, with no idea what you meant by it.

So if there is any way to rack up reward that does not serve your real goal, the agent will find it and exploit it: a cleaning robot rewarded for 'no visible mess' learns to knock over the bin and cover it up; a game agent rewarded for points farms a meaningless loop forever. These are not malfunctions — the agent did exactly its job, climbing the score it was given. The gap between the reward you wrote and the outcome you wanted is where all the trouble lives, and the agent will pour into any crack you leave open. This is the central hazard the next two ideas try to contain.

Leash the agent to a known-good starting behavior

J(θ) − β·KL(π_θ ∥ π_ref) where π_ref is a frozen, known-good policy
One guardrail against that exploitation: do not let the agent wander too far from a sensible reference behavior while it chases reward.

Alongside 'get more reward,' add a second pressure: 'do not drift too far from how the trusted reference agent would act.' A dial sets how tight that leash is. Loose, and the agent is free to roam into reward-hacks far from anything sensible; tight, and it stays close to the known-good reference, collecting reward only through small, sane deviations. This is precisely the bargain behind tuning large language models from human feedback: chase the reward, but stay recognizably close to the well-behaved starting point — so you gain what the reward captures without careening off into its loopholes.

The hard part is writing a reward that means what you want

Given the policy and the loss, the math is deterministic. Specifying r such that climbing it serves your goal is open-ended.
Everything above — nudging the odds, comparing to normal, following the slope — is mechanical once the reward exists; the machinery will faithfully climb whatever score you hand it.

The genuinely hard, unsolved part runs the other way: writing down a reward such that climbing it actually produces the behavior you have in mind. There is no formula for that. 'Win the game,' 'drive safely,' 'be helpful' all have to be boiled down into a single number, and every clumsy translation leaves a crack the agent will pry open, exactly as in the reward-hacking idea. So the real craft of the field is not the update rule — it is this inverse puzzle of reward design, which has no perfect answer and is where most of the effort, and most of the failures, actually live.

The approaches, as variations on the math

Reinforcement-learning methods turn a few dials on the same core.

How the odds are nudged. From the total episode reward, or from finer per-step estimates of how good each situation is, which steadies the signal. What 'normal' to subtract. A learned estimate of the usual return from each situation, so the agent reacts to surprise rather than to the raw number. How the agent is kept sane. A leash to a trusted reference behavior, tightened or loosened by a dial, to block reward-hacking. How the reward is built. Hand-written, learned from human preferences, or inferred from demonstrations — because writing the reward directly is the crack-prone part. The thread never changes: improve by shifting the odds of moves toward the ones that paid off better than expected, and remember the agent optimizes the letter of the reward, so the real work is making that letter match your intent.

A worked numeric example

If two sampled actions get rewards 1 and 0 with baseline 0.4, their advantages are 0.6 and -0.4. The log-probability of the first is increased; the second is decreased. RL is probability mass moving toward actions that beat expectation.

1Aligning generation with reward: preference optimization for images and video
R_pair = logit(π(y_better) - π(y_worse)) + λ·KL(π‖π_ref); train consistency/style/detail rewards as separate models, then combine via weighted sum to steer image/video generation
Preference learning works by scoring pairs of outputs (one good, one bad) and using the log-odds difference — the advantage in logged probabilities between them — as the reward signal. Each task goal (keeping details stable, matching a style, staying true to the input) is learned as a separate reward model, then combined by adding them with weights, avoiding the single-objective hacking problem because competing goals balance explicitly.
These papers learn rewards for image and video generation by comparing pairs of outputs and measuring how much one is better than the other. They break the reward into separate pieces — one for keeping colors steady, one for matching the desired style, one for preserving detail — so each goal can be balanced against the others without one hijacking the entire training.

2Reasoning by reward: GRPO for multimodal LLMs

3Designing the reward: reward models, curricula, and the hacking problem
Curriculum: difficulty β(t) = initial + ramp·t; variance filter σ²(traj) to select high-information samples; token-reward decompose coarse r via ∇r · δtoken (first-order attribution)
Defense against hacking uses three tools: (1) gradually increasing task difficulty over time so the policy cannot get stuck in easy shortcuts, (2) picking training samples where the reward is most informative — cases where the model is uncertain — so the policy learns what matters, and (3) breaking down the reward into pieces per decision step, so the policy learns which specific choices earned the points, not just that some aggregate score went up.
These papers directly address reward hacking — when a policy exploits loopholes in the reward specification. They use three defenses: gradually making tasks harder so the policy cannot stay stuck in easy exploits, picking training examples where the reward signal is clearest, and breaking rewards into per-step components to clarify which decisions earned which points.

4Reward for perception: RL where the goal is not differentiable
Two-stage: supervised pretraining learns critic π_clip from CLIP labels; hierarchical RL optimizes π with chunk-level temporal rewards R_t = consistency(frame_t, frame_t-1) + relevance(frame_t)
Perception tasks like picking key moments in a video have no slope to follow, so RL uses two stages: first, train a score function on a related task (a built-in relevance model), then fine-tune with RL using explicit time-based goals like 'keep the picture steady between frames' and 'pick frames that matter.' Breaking the problem into time chunks reduces noise by structuring which steps affect which rewards.
These papers learn from perception tasks — picking moments in video, finding objects in images — where you cannot write a math formula for what is correct. They first learn a scoring function from labeled examples, then fine-tune with RL using explicit time-based or spatial goals.

5Learning to move: RL for legged locomotion and agile control
Trajectory reward R_traj = Σ[v_desired·v_actual + τ·(load_state - load_pred)] where load_state tracked by built-in model; contrastive goal reward R_goal = log(sim(video_demo, video_rollout) / sim(video_demo, random_video))
Walking robots learn to handle unseen forces (load on the leg, thrust from the thruster) by bundling a forward predictor into the reward: the robot learns the effects of its own hidden state and compares prediction to reality, feeding both into the score. Goal rewards can come from video examples alone (no action labels) by treating the demo video as the target and random videos as anti-targets, scoring based on perceptual closeness without asking for manual labels.
These papers train robots and simulated creatures to move — walking, swimming, responding to unknown forces. They ground rewards in physics (tracking forces, matching thrust), use video examples instead of action labels, and pre-train on easy tasks before learning hard ones.

6Reward at scale: RL for multi-robot coordination, exploration, and assembly

These papers extend RL to teams of robots and large-scale manipulation tasks. They use learned routing between options, keep a base safe behavior frozen while training a correction layer, and initialize teams in easy configurations then gradually expand their world.
