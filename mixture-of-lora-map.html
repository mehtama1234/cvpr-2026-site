The mixture-of-LoRA design space

Fifty-plus methods, one question: once a skill is a low-rank delta, how do you keep many of them and arbitrate between them without them interfering? Here is the whole field on four axes, each method read from first principles, with our three hands-on builds pinned as reference points.

Why this problem exists at all

Start from the thing everyone actually wants: one model that can do many things well. The obvious way — fine-tune the whole model on everything at once — fails for a concrete reason. Skills fight. Teaching the same weights to do math and to rewrite text and to follow a strict format pulls them in different directions; the shared parameters average the conflict and every skill comes out mediocre. That is interference, and it is the enemy the whole field is organized around.

LoRA changed the game by making a skill cheap and separable: freeze the big model, and store each new skill as a tiny low-rank delta — a few megabytes you can keep on a shelf and snap on. Now skills don't have to share weights, so they don't have to fight. But that just moves the hard question one step down the road: if every skill is its own little module, how do you hold many of them at once and decide how much of each to use for a given input — without reintroducing the interference you just escaped? Every method below is an answer, and they differ on exactly four choices.

The four axes (and the real tradeoff behind each)

① What is an expert? — the granularity choice

"Expert" just means a piece of skill you can switch on or off. The first decision is how big that piece is, and it is a genuine tradeoff, not a detail. Make each expert a whole adapter and it's a complete skill you trained and can name ("this is the math one") — legible and self-contained, but coarse: you can't use half of it, and you must store one per skill. Grow experts inside the FFN and they're sub-networks the model carves out for itself during training — finer and cheaper to run sparsely, but anonymous (you only learn what each does by inspecting it, as we did). Make each rank an expert and you're routing over the rank-1 atoms a LoRA is already built from — maximal granularity at almost zero extra cost, but each atom is tiny and can't hold much alone. The dot to connect: granularity trades legibility and per-expert capacity against flexibility and thrift. Bigger pieces are clearer and hold more but combine coarsely; smaller pieces combine in more ways and cost less, but each knows less and their specialization gets harder to read.

② How are experts combined? — the arbitration choice

Once you have pieces, something must decide how much of each to use — and the deep split is when that decision happens. Decide it once, offline and you merge: average the pieces into a single adapter. Nothing extra to run, blazing fast — but the blend is frozen, so a merged model can't lean on math for one input and formatting for the next. Decide it every time, at inference and you route: a small network looks at the input and mixes experts on the fly. Adaptive per input — but you pay to run the router (and, in designs like X-LoRA, to run the model twice). A third path, router-free aggregation, tries to combine without a learned gate at all, dodging both the router's cost and its failure modes. The through-line: merging buys speed by giving up per-input adaptivity; routing buys adaptivity by paying compute. Half the papers on this map are one attempt to get routing's flexibility at merging's price.

③ How does the router decide? — the decision-rule choice

If you route, the router needs a rule for reading a token and choosing experts. The default is a small learned softmax gate — read the hidden state, emit a soft preference over experts, train it with everything else. Simple and differentiable, but soft gates are wishy-washy (our own X-LoRA baseline barely committed — 0.36 on a three-way choice) and can collapse onto one expert, which is why methods bolt on a load-balancing loss. So the variants harden the decision: pick the single best expert (hard selection) for crispness and compute savings; train the router with reinforcement learning when "which expert was right" isn't something you can differentiate (reasoning, tool use); or route on the query / sub-token so the same word can pull different skills in different contexts. Underneath, the router is just a classifier of "what kind of token is this" — and each variant is a different bet on how confident and how discrete that classification should be.

④ Dense or sparse? — the commitment choice

Finally, how many experts actually fire. Blend all of them (dense) and you never miss a useful one, but you pay to run every expert and the blend stays muddy — nothing specializes hard because every expert sees every token. Fire only the top-k (sparse) and you commit: cheaper (unpicked experts never run) and sharper (each expert sees only the tokens it owns, so it specializes harder — exactly why our rank build routed math and format to different ranks so cleanly), but brittle when a token genuinely needs a skill the router didn't pick. It's the same commit-early-to-go-fast knob as everywhere in engineering. Our three builds sit right on it: X-LoRA dense and soft, MixLoRA and rank-as-expert sparse and sharp.

The trilemma the four axes are really about. Step back and the choices collapse into three forces pulling against each other:
  • Specialization — experts that genuinely differ, so combining them adds real skill (not just averaging).
  • Non-interference — skills that don't corrupt each other or the frozen base (the reason naive merging can "collapse").
  • Efficiency / mergeability — cheap to store, combine, and run.

You can buy any two by spending the third. Sharp sparse routing maximizes specialization but risks interference at the token boundaries and costs a router. Static merging maximizes efficiency but blurs specialization into an average. Whole-adapter experts are legible and interference-free but coarse and heavy to store. Every method on this map is a wager about which corner it can afford to give up least — which is precisely why there are fifty of them and no single winner.

Per-method deep-reads

Grouped by their answer to the first, deepest question — what is an expert?

Experts are: A whole adapter (12)

X-LoRA we built

Dense mixture of frozen LoRA experts gated by learned hidden-state-dependent scalings

The problem. Combining multiple pre-trained LoRA adapters without destroying individual expert knowledge through arithmetic merging, while maintaining parameter efficiency. Standard merging loses specificity; naive mixture-of-expert approaches either add computational overhead or require retraining.

The approach. Freeze all LoRA adapters and the base model. Learn only a small feed-forward gating head that takes hidden states and predicts softmax-normalized scaling weights λᵢ per adapter per token per layer. Scale each LoRA's output by its gated weight and blend additively. Execute two forward passes per step: first to gather hidden states, second to apply learned scalings.

What's unique. X-LoRA's signature is dense softmax gating (not sparse top-k routing) combined with layer-wise application of the same gating head. This lets the model dynamically reweight all domain experts simultaneously at every layer and token, enabling complex learned blending patterns unavailable in static merging or sparse-routing MoE systems. The dual forward pass reflects a design principle from molecular biology: reuse frozen building blocks in different hierarchical contexts rather than train new experts.

The fundamental point. Frozen expert LoRAs can be recombined at inference through a learned lightweight gating function that runs on hidden states, avoiding knowledge loss while staying parameter-efficient. The key insight: soft blending of all experts (not discrete routing) preserves each adapter's distinct knowledge while learning task-aware mixing.

MoLE (Mixture of LoRA Experts)

Learn per-layer routing weights to dynamically blend pre-trained LoRA experts.

The problem. Combining multiple trained LoRAs via direct arithmetic merging causes generative collapse when low-rank updates dominate the original weights, while reference-tuning methods require expensive retraining to change composition. Neither preserves the pre-trained model's core identity nor the distinct characteristics of individual LoRAs.

The approach. MoLE treats each layer of pre-trained LoRAs as an immutable expert and trains a lightweight gating network per layer that learns a softmax probability distribution over experts. The gating function takes concatenated expert outputs, reduces them through a learnable matrix, and applies softmax with learnable temperature to compute continuous weights for blending. This decouples expert training from composition strategy, enabling flexible zero-cost inference-time masking.

What's unique. MoLE's layer-wise (hierarchical) gating is its defining strength: different transformer depths can route differently to the same set of LoRA experts, giving fine-grained per-layer control. Unlike sparse top-k routing that excludes experts, softmax routing keeps all experts present and continuously blended, preserving their full identity. No retraining is needed to mask unwanted LoRAs at inference—pure flexibility with minimal computational overhead.

The fundamental point. MoLE establishes that LoRA composition is fundamentally a learned routing problem, not an arithmetic or retraining one. By respecting the layer structure of transformers and making routing per-depth rather than global, it shows that expert blending strategies must be depth-aware: the optimal way to combine LoRA contributions changes across layers.

MoLA

Layer-wise LoRA expert allocation with more experts in higher layers, fewer below

The problem. Transformer layers exhibit varying complexity and specialization needs, yet standard parameter-efficient and mixture-of-expert approaches allocate experts uniformly across layers, creating redundancy in simple lower layers while under-resourcing specialized higher layers that learn abstract task-specific patterns.

The approach. MoLA allocates a different number of LoRA experts per layer—fewer specialists in lower layers, more in higher ones—guided by an inverted-triangle or learned schedule. A softmax gate routes each token to the top-K experts at that layer; each expert is a paired low-rank matrix combined via weighted summation with frozen base weights.

What's unique. Most prior mixture-of-LoRA methods apply uniform expert counts across all layers. MoLA's distinction is the discovery that layer function determines optimal expert allocation: lower layers exhibit high expert redundancy and perform well with few specialists, while higher layers benefit from more diverse, specialized experts. The inverted-triangle pattern (more experts in higher layers) outperforms all uniform baselines while consuming fewer parameters.

The fundamental point. Expert allocation in LoRA-based MoE is not uniform: layer abstraction level and functional diversity should dictate specialist count. Efficiency emerges not only from sparse routing but from deliberately mismatching expert density to layer needs—removing redundancy from early layers, concentrating specialization in later ones.

Mixture-of-LoRAs

Route domain-specific LoRA adapters via sequence-level gating to prevent multitask interference.

The problem. LLMs fine-tuned on multiple domains suffer task interference and catastrophic forgetting—shared parameter updates from one task degrade performance on others. Standard multitask tuning either forces a single compromise model or allocates prohibitive parameter budgets. The core tension: how to achieve both domain specialization and model efficiency without the model unlearning what it mastered on prior tasks.

The approach. Train N domain-specific LoRA modules independently on separate datasets, then stack them as experts with a sequence-level router (two-layer MLP) that assigns entire input sequences to the appropriate expert(s) based on domain metadata. Each transformer layer gets its own router; during training, both the LoRA modules and routers are optimized jointly via a combined loss (language modeling + domain classification). At inference, routers vote or use the final layer's decision to select experts when domain labels are unavailable. Weight computation: W₀ + router(Wᵣ, A₁B₁, ..., AₙBₙ) where W₀ is frozen base weights and each AᵢBᵢ is a LoRA adapter.

What's unique. Unlike standard MoE which trains sparse tokens across experts and softmax-gates at token granularity, this method exploits sequence-level domain signals known at input time. The router doesn't learn implicit task assignments through mixture weights; instead, domain labels guide explicit routing decisions. LoRA modules start pre-trained on their own domain, preserving specialization, rather than training experts from scratch. The routing mechanism adds only 1.05M parameters—remarkably lean compared to dense expert networks—and preserves full base model access. Crucially, it prevents cross-task interference by isolating LoRA updates per domain during the training phase, then coordinating access at inference through the learned router.

The fundamental point. The core insight is that multitask interference in LLMs is not a routing problem first—it is a parameter-update isolation problem. By training each domain's adapter independently before routing, the model never asks the shared base parameters to simultaneously satisfy conflicting objectives. The router then becomes a lightweight coordinator rather than a load-balancer struggling to resolve interference after the fact. This inverts the typical MoE philosophy: specialize experts *before* combining them, not during.

FURINA

Router-free mixture-of-LoRA via linear aggregation of direction-magnitude decoupled experts

The problem. Existing mixture-of-LoRA methods use discrete routers to activate experts, which prevents merging the adapters back into the backbone model after training. This forces separate adapter execution at inference time, creating computational overhead and preventing deployment in production LLM frameworks that require mergeable LoRA.

The approach. FURINA decouples LoRA adapter direction and magnitude components and learns them separately. Multiple expert adapters activate based on angular similarity between input and each adapter's directional component, then scale uniformly via a shared learnable magnitude vector. The output norm naturally reflects expert importance. An expert selection loss encourages sparse activation. After training, experts linearly aggregate into a single LoRA or merge directly into the backbone with zero inference cost.

What's unique. FURINA is the first fully mergeable MoE-LoRA method—competitors like MixLoRA and LoRAMoE cannot eliminate router overhead at inference. FURINA proves that routing signals emerge from adapter geometry (angular similarity + magnitude scaling) rather than requiring a learned router network, making capacity expansion and mergeability compatible.

The fundamental point. FURINA establishes that mixture-of-LoRA routing can be expressed as a continuous, geometric property of decoupled adapter components rather than a discrete router, enabling lossless merging while preserving multi-expert capacity during training.

MALoRA

Mixture of asymmetric LoRA experts with shared down-projection subspace for multi-task learning

The problem. Multi-task learning with LoRA creates a structural mismatch: down-projection matrices show high similarity across tasks (redundant), while up-projections show low similarity (genuine task-specific variation). Standard mixture-of-experts wastes parameters on redundancy while under-investing in real task divergence, and suffers training imbalance where gains in one task degrade others.

The approach. MALoRA exploits observed asymmetry by making unequal architectural bets across experts. It factors down-projections as A_t ≈ P_t·S_A (shared global subspace S_A reused via task-specific coefficients P_t) while raising up-projection ranks (B_t) to preserve task-specific capacity. Routing remains per-input top-K softmax over 8 sparse experts; outputs combine via weighted summation of activated experts.

What's unique. Unlike MoLoRA which treats all LoRA matrices symmetrically, MALoRA allocates capacity asymmetrically based on empirical patterns: it factorizes the redundant down-projections via shared subspace factorization while expanding up-projection capacity. This direct targeting of observed redundancy cuts parameters 30-48% and gains 1.2x speedup while avoiding the overfitting MoLoRA shows at high ranks.

The fundamental point. Parameter efficiency in multi-task adaptation emerges not from uniform compression but from recognizing which learned dimensions genuinely diverge across tasks. By coupling high-rank output projection (task-specific) with factorized input projection (shared subspace plus task coefficient), MALoRA makes efficiency a natural consequence of task geometry rather than an external constraint.

MoSLD

Shares upper LoRA matrices across experts while keeping lower matrices task-specific, with dropout regularization for multi-task efficiency.

The problem. Multi-task learning with LoRA suffers from knowledge interference across domains and parameter explosion when adding experts. Standard mixture-of-experts approaches either fail to handle domain conflicts or introduce computational overhead that negates efficiency gains from parameter sharing.

The approach. MoSLD enforces that the upper projection matrix (A) is shared identically across all experts in a layer—forcing universal feature learning—while the lower matrix (B) remains task-specific. A top-K softmax routing gate selects sparse experts, and dropout is applied to shared A matrices to prevent imbalanced parameter updates and overfitting.

What's unique. Unlike MoLora (separate experts per task) or other mixture-of-LoRA methods that keep A and B independent per expert, MoSLD splits the responsibility: A learns general cross-task patterns while B focuses on task distinctions. The dropout strategy on shared parameters is novel—it directly addresses parameter balancing pathologies that emerge when one matrix is reused across multiple experts.

The fundamental point. Selective parameter sharing in LoRA mixture-of-experts can reduce interference and parameters simultaneously—forcing experts to agree on universal representations forces useful knowledge sharing, while task-specific low-rank projections preserve adaptation capacity without the overhead of full expert separation.

SLIM

Mixture-of-LoRA with identity routing to learn new skills without forgetting base knowledge.

The problem. Fine-tuning language models creates a hard tradeoff: task-specific adapters learn new capabilities but overwrite base model knowledge, causing catastrophic forgetting. Standard PEFT methods cannot balance downstream performance with retention of general-purpose abilities because all computation is forced through the adapted parameters.

The approach. SLIM introduces identity (passthrough) layers as explicit experts alongside LoRA adapters, enabling selective bypass of adaptation. A learnable routing function R̂(x) decides per-input whether to apply the LoRA adapter or skip it entirely, using weight-yielding with sliding clustering to align routing decisions to input distribution. This allows downstream task samples to route through adapters (learning) while out-of-distribution queries bypass them (preserving general knowledge), reformulated as dynamic model merging.

What's unique. SLIM treats "do nothing" (skip adaptation) as a first-class expert choice via identity mixture, directly addressing the root cause of forgetting rather than managing multiple task adapters. The distribution-aware routing mechanism uses input clustering instead of learned gate networks, making routing depend on data properties rather than parameter-driven attention, which reduces routing bias. This reframing makes catastrophic forgetting optional—it emerges from forcing all computation through adapters, not from learning itself.

The fundamental point. Selective merging guided by input distribution recovers forgotten knowledge without data replay. By allowing certain queries to bypass task-specific parameters, models retain base behavior for those cases while gaining new capabilities for in-distribution tasks. Forgetting is a design choice, not an inevitability.

PERFT

Mixture-of-experts fine-tuning via routed adaptation experts aligned with native MoE routing

The problem. MoE models' efficiency derives from dynamic routing among specialized experts, yet standard PEFT treats them as dense networks, ignoring this core architectural property. Full fine-tuning remains prohibitively expensive due to vast expert parameters and unique routing challenges unseen in dense models.

The approach. Introduce multiple bottleneck adaptation experts (down-project, activate, up-project) with independent or reused gating networks that route tokens to different PEFT experts. Four variants trade off: PERFT-R learns independent routing for adaptation experts; PERFT-E reuses the pretrained MoE router; PERFT-D uses always-on dense experts; PERFT-S single expert baseline.

What's unique. Unlike mixture-of-LoRA methods that bolt MoE routing onto dense-model LoRA, PERFT operates natively within MoE architectures and leverages existing expert structure. It creates a second routing dimension at the PEFT layer, enabling task-specific expert activation patterns that MoE-agnostic methods miss. Independent routing can unlock more expressive adaptation space than dense alternatives.

The fundamental point. MoE architectures demand multi-expert, dynamically-routed adaptation to match their underlying sparsity—a single global adapter cannot efficiently serve the diverse, expert-specific specialization that the base model has learned.

LoRAHub

Compose pre-trained LoRA modules via gradient-free weight optimization for cross-task generalization.

The problem. Large language models must adapt to new unseen tasks efficiently with few examples. Current approaches force a choice between fast zero-shot inference (inaccurate) and slow few-shot in-context learning (token-heavy). The gap stems from inability to cheaply reuse task-specific adaptations already trained on other domains—requiring either rerunning expensive inference or training new adapters from scratch.

The approach. LoRAHub fuses multiple pre-trained LoRA modules via element-wise weighted combination—each module m_i = A_i × B_i is linearly combined with scalar weights {w₁, w₂, ..., wₙ} to produce a composite adapter. Given a handful of target-task examples, CMA-ES (a gradient-free black-box optimizer) tunes those weights by minimizing task loss plus L1 regularization, returning fixed per-task coefficients without backpropagation.

What's unique. Unlike retrieval-based or dynamic-routing mixture-of-LoRA methods, LoRAHub uses static task-level composition—one fixed weight vector per task, no per-request routing. It refuses gradient-based training entirely: no hypernetworks, gating layers, or multi-task retraining required. Takes any library of vanilla LoRA modules trained independently and produces scalar blending weights via black-box optimization, making it CPU-compatible and architecture-agnostic.

The fundamental point. Low-rank adapter composition can be learned without gradients by optimizing scalar mixing weights via black-box search, and element-wise linear blending of independently trained LoRA modules suffices to achieve near few-shot performance at zero-shot inference speed—proving that the bottleneck is token efficiency, not adaptation complexity.

Stronger MoLE (MoELoRA Riemannian)

Stabilize mixture-of-LoRA training via Riemannian-preconditioned, gate-aware gradient scaling.

The problem. Fine-tuning foundation models with multiple low-rank experts improves expressiveness over single LoRA, but existing MoE-LoRA exhibits training instability and weak inference robustness. The core issue: when gates dynamically weight expert contributions, the effective geometric structure of gradient descent shifts per expert, but standard optimizers and preconditioners treat all experts identically—creating inconsistency between optimal descent in low-rank manifold space versus full-rank gradients.

The approach. The method applies Riemannian gradient preconditioning (inspired by manifold geometry) to mixture-of-LoRA training, augmented with gate-value-aware rescaling. Instead of treating each expert's low-rank subspace equally, it detects that gate multipliers (g_i) alter the manifold curvature distinctly per expert. During backward pass, preconditioner scaling is divided by gate values to correct for this effect, while forward pass maintains gate consistency via selective gradient detachment. The result: experts train in geometrically-coherent subspaces despite dynamic gating.

What's unique. Prior MoE-LoRA methods (e.g., LD-MoLE, vanilla MoELoRA) stack multiple LoRA experts with softmax routing but ignore the interaction between gating and low-rank manifold geometry. This work is first to recognize that gate-weighted expert combinations create misaligned gradient flow—where a gate scaling the expert's update also scales its manifold curvature, yet standard preconditioners don't account for this. The gate-rescaled preconditioning directly addresses optimization geometry, not just routing architecture or expert composition.

The fundamental point. The core insight: mixture-of-experts in low-rank spaces is fundamentally a problem of multi-manifold optimization, not just weighted averaging. When gates modulate expert contributions, they implicitly reweight the geometric landscape (curvature) each expert operates on. Stabilizing MoE-LoRA requires gradient preconditioning that adapts to gate values, ensuring all experts descend along their respective manifold geodesics despite dynamic weighted mixing.

MixtureKit

Framework to compose pretrained models into MoE architectures with flexible routing and visualization.

The problem. Retraining MoE models from scratch wastes compute; existing tools lock you into specific model families (Mixtral) or require hand-coded architecture support for each new base model. The gap: how to recycle knowledge in pretrained checkpoints into MoE without rebuilding per-architecture and without expensive training.

The approach. Configuration-driven pipeline: declare base model, expert models, and routing strategy (Traditional MoE, BTX, or BTS); MixtureKit auto-patches model architecture via regex matching, trains routers or stitch-layers via LoRA, and outputs a single unified checkpoint ready for inference or fine-tuning. Routers use top-k gating to select sparse expert subsets per token.

What's unique. Regex-based architecture adaptation (not hardcoded per-family) enables generalization across Llama, Gemma, Mixtral, etc. Pairs expert composition with visualization tools (per-token routing inspection, layer-wise expert contribution analysis) to diagnose routing collapse and expert specialization—not just a static merge.

The fundamental point. Demonstrates that expert composition is decoupled from base architecture: routing and stitch-weight adaptation alone (LoRA-trainable) can transform any pretrained model into a working MoE without retraining. This shifts MoE from specialized training pipelines to declarative model recombination.

MixLoRA we built

Sparse mixture-of-LoRA experts fused into frozen FFN layers, routed via top-k gating with load-balance auxiliary loss.

The problem. Fine-tuning large models faces dual pressure: parameter-efficient methods like LoRA sacrifice performance in multi-task scenarios, while mixture-of-experts models consume prohibitive GPU memory. Existing LoRA-MoE hybrids place multiple LoRAs within single transformer sublayers or duplicate FFN weights across experts, incurring training overhead and memory waste without realizing clean separation of base computation from task specialization.

The approach. MixLoRA replaces each FFN block in a frozen pre-trained model with a sparse MoE structure where all experts share the same frozen weight matrices, but each expert applies a distinct low-rank adaptation (B·A pair). A learned top-k router selects the k most relevant experts per token via softmax gating. During training, an auxiliary load-balance loss term (L_aux = a·N·Σ(F_i·P_i)) penalizes imbalanced expert activation, ensuring uniform workload distribution across tasks. Independent attention-layer LoRA adapters run in parallel to capture attention-specific adaptations.

What's unique. MixLoRA distinguishes itself by cleanly factoring MoE computation: shared frozen base weights eliminate weight duplication (unlike native MoE experts), while isolated LoRA modules per expert decouple task knowledge from shared representations. This aligns MixLoRA with production MoE architectures (Mixtral 8x7B) rather than previous LoRA-MoE methods that inserted multiple LoRAs into single transformer blocks or forced redundancy. The dual-adaptation design—FFN expert routing plus independent attention LoRAs—enables task-specific refinement without the training friction of prior approaches.

The fundamental point. MixLoRA establishes that mixture-of-experts and parameter efficiency are orthogonal rather than competing objectives: by keeping base computation frozen and routing only through learned low-rank updates, you gain sparse conditional computation (9% accuracy lift in multi-task, 40% memory savings, 30% latency reduction) without the weight explosion or training instability of dense MoE or naive LoRA-MoE hybrids.

ReMix

Reinforcement-routed equal-weight LoRA mixtures that prevent expert collapse during finetuning.

The problem. When combining multiple Low-Rank Adapters (LoRAs) for LLM finetuning, learned routing weights naturally collapse to concentrate on one or two dominant adapters—wasting computation on inactive experts and crippling the model's ability to specialize across different skill dimensions. The root issue: learnable soft-mixture weights optimize toward single-LoRA solutions because the loss landscape rewards ignoring redundant experts.

The approach. ReMix replaces learned routing weights with fixed equal weights across the k selected LoRAs per layer, guaranteeing all active experts contribute meaningfully (Effective Support Size = k, never collapsing to 1). Since equal weights are non-differentiable, the method shifts training to a reinforcement learning frame: a learned router selects which k LoRAs to activate per input, using RLOO (Reinforce Leave-One-Out) to estimate gradients where the finetuning loss serves as negative reward. At inference, the router switches to deterministic top-k selection.

What's unique. Most prior mixture-of-LoRA work (LoraHub, HydraLoRA, S'MoRE) still relies on learned routing weights that exhibit the same collapse behavior—different initialization tricks or decomposition strategies but fundamentally the same optimization pressure. ReMix alone decouples weighting (fixed) from selection (learned), treating expert activation as a discrete combinatorial choice rather than a soft probabilistic mixture. This is unique: prior work assumes you can smooth the selection problem; ReMix proves the smoothing itself is the pathology.

The fundamental point. Equal-weight fixed routing with learned discrete selection fundamentally changes mixture-of-LoRA from a soft aggregation problem (how much each expert contributes) to a hard assignment problem (which experts participate). This reveals that the real optimization target in mixture-of-experts should be selection quality, not weight fine-tuning—a first-principles shift from continuous routing to combinatorial routing that extends beyond LoRAs to any modular expert system.

Experts are: A single rank (2)

FlyLoRA

Rank-wise mixture-of-experts LoRA using frozen random projections and implicit top-k routing without trainable routers.

The problem. LoRA fine-tuning suffers from parameter interference both within tasks (intra-task: conflicting rank updates) and across tasks (inter-task: overlapping LoRA adapters in merging scenarios). Existing mixture-of-experts LoRA variants address only single-task interference while introducing trainable router parameters that negate the parameter-efficiency motivation for using LoRA in the first place.

The approach. FlyLoRA treats each rank (rank-1 decomposition b_i * a_i^T) as an individual expert and gates them via a frozen sparse random projection matrix A that remains fixed throughout training. This projection maps inputs into a higher-dimensional space where top-k selection by magnitude acts as implicit routing, eliminating explicit router parameters. The frozen matrix's approximate orthogonality properties naturally segregate different tasks into decorrelated subspaces, preventing interference during multi-task merging.

What's unique. Unlike prior MoE-LoRA methods that add trainable routers (increasing parameters and compute), FlyLoRA eliminates the router entirely by repurposing the down-projection as an implicit gate. Its rank-level granularity (each rank = one expert) is finer than layer-level MoE. Bio-inspired by fly olfactory circuits (random projection + sparse activation), it achieves task decoupling through mathematical properties of frozen random matrices rather than learned routing policies.

The fundamental point. FlyLoRA establishes that mixture-of-experts can emerge implicitly from frozen geometric structure without trainable routers: random projections naturally create approximate orthogonal subspaces that decouple task-specific LoRA components, proving that parameter efficiency and multi-task robustness need not require explicit gating mechanisms.

SMoE-LoRA (SMoRA)

Treats each LoRA rank dimension as an expert with dynamic rank-wise gating for multi-task learning.

The problem. Multi-task LoRA adapters face a fundamental tension: vanilla LoRA's shared parameters create task interference, while existing Mixture-of-Experts approaches that treat entire LoRA modules as experts isolate knowledge and fail to exploit commonalities across related tasks. Current MoE-LoRA systems choose between full module specialization (coarse-grained, wasteful) and complete sharing (insufficient task separation).

The approach. SMoRA decomposes LoRA into rank-level components and applies dynamic gating at the rank dimension. Instead of routing complete LoRA modules, a learned gate selects the top-k ranks per task input using softmax-normalized top-k routing. This partitions a single LoRA weight matrix into rank-wise experts, enabling each rank to specialize independently while remaining within a unified structure that facilitates knowledge exchange across tasks at finer granularity.

What's unique. Unlike module-level MoE-LoRA (HydraLoRA, MoSLoRA) that route entire adapters, SMoRA routes at rank granularity—the finest practical level. It unifies single-LoRA and multi-LoRA MoE through a theoretical equivalence: dynamic multi-LoRA routing equals rank partitioning within one LoRA. This rank-level routing enables selective sharing (some ranks task-specific, others shared) rather than binary all-or-nothing decisions, achieving both deeper task specialization and richer knowledge blending than coarser approaches.

The fundamental point. The insight is that LoRA decomposition's low-rank structure naturally admits expert granulation at the dimension level: each rank can be independently specialized to different tasks while maintaining a tight coupling that preserves shared semantics across the rank space. This reveals that the optimal expert unit is not the module (too coarse) nor the neuron (too fine), but the rank—the natural factorization boundary in low-rank adaptation.

So which do you actually pick?

Read the axes backwards from your situation and the fifty methods collapse into a handful of decisions:

  • You already have separate trained adapters and just want them to work together → compose them with a gate (X-LoRA, MoLE) if you want per-input adaptivity, or merge them into one (LoRAHub, mergekit) if you want zero inference overhead.
  • You want one efficient model that does several things, trained fresh → grow experts inside it (MixLoRA), sparse top-k so you also get the compute savings.
  • You're squeezed on parameters or memory → go finer-grained — rank-as-expert (FlyLoRA, SMoRA) adds routing with almost no new weights.
  • You need to serve thousands of task-specific adapters to different users → this isn't a mixture problem at all; use a serving system (LoRAX, vLLM) that hot-swaps one adapter per request.
  • Your "which expert was right" signal isn't differentiable (reasoning quality, tool success) → route with reinforcement learning (ReMix) or hard selection instead of a soft gate.
  • Your worry is forgetting the base model's abilities → the continual-learning branch (SLIM) keeps an identity path so new skills add without overwriting old ones.

The honest summary from our own three builds: routing genuinely works — a gate does learn to send the right tokens to the right skill — but it is soft by default and only gets crisp when you force commitment (cold temperature, sparse top-k, or fine-grained rank experts), and it only helps where the skills are truly distinct (our JSON task never earned its own expert in any build, because the base model already knew how). Modularity buys you a lot; it does not buy you a skill the model didn't need.
