Mixture of experts — why it works, mathematically

Turn on only a few specialist networks per token, so you can grow the model's knowledge without growing the compute cost per token—but only if the router that picks which experts can actually learn without breaking down and always picking the same one.

Plain-English big picture

What this is really about

A mixture of experts stores many specialist networks but uses only a few for each input. A router decides which experts should handle the current case.

Where topology and shape enter

Topology appears in the routing map. Inputs that are close in meaning should often go to similar experts, while different regions of the data surface can be served by different specialists.

Where the same idea appears elsewhere

MoE is used in language models, vision, recommendation, retrieval, and large multi-task systems.

Why Mixture of experts is worth learning

It matters because it gives a model more capacity without paying the full cost on every example.

The problem, as a quantity

A model with d parameters must run all d of them every single time a token arrives. To know more, you add more parameters: a model with twice as many costs twice as much compute per token. The real problem is deeper: every piece of the network, whether it helps or hurts on this particular token, gets computed anyway. Some weights are specialists in rare events; running them on common tokens is pure waste. So the hard question is: how do you let the model choose a tiny fraction of its weights to actually run per token, and learn to make that choice just from the signal it gets right or wrong? A hard choice has no path for learning to flow backward through. A soft choice using softmax (turn scores into shares that add up to 1) on all experts brings back the full compute you tried to escape. You need a learned routing function g(x) that picks a real subset of experts but still allows learning to flow backward through it—and without careful design, the router will collapse into picking the same expert always, turning your specialists into one overworked generalist.

The core ideas — and why they work

Sparse routing via soft top-k gating

y = Σᵢ∈topk gᵢ(x)·Eᵢ(x), g(x) = softmax(router(x)), k ≪ N
A token x arrives. A small neural network (the router) reads it and outputs a score for each expert. You convert these scores into shares: numbers that are all positive and add up to exactly 1. But you do not compute all experts—you only run the k experts with the highest shares. The final output is a weighted sum of those k experts' outputs, using the shares as the weights. Why does this work? Because the share conversion is smooth and gradual (not abrupt), the path for learning to flow backward goes all the way to the router. So the router learns to give high shares to experts that reduce mistakes. Here is the key: the choice of which experts uses smooth shares (no hard on-or-off), but the actual compute is sparse (only k run). You get the signal you need to learn what matters.

The routing collapse: one expert hoards all tokens

Collapse: g(x) → [0, …, 0, 1, 0, …, 0] for all x (argmax, entropy → 0)
Without guardrails, a learned router hits a fatal problem. Early in training, one expert (by luck) gets slightly more tokens and improves its mistakes faster. It gets more attractive, pulls more tokens, improves even faster—a self-reinforcing spiral. Within a few steps, the router stops exploring: it always picks the same expert for every input, ignoring the input details entirely. The shares become nearly zero for all but one expert, and your mixture of N experts becomes a single pathway—no capacity gain, no benefit. This collapse is a deep flaw whenever one mechanism learns to pick from many options with no opposing force.

Load-balancing loss forbids collapse

ℒ_load = λ·Σⱼ(Σᵢ gᵢ(x^(i))_j)² / (k·|batch|), target ≈ k/N per expert
To keep experts alive and diverse, add a penalty if some experts get too many tokens and others get too few. Over a batch (a chunk of tokens), measure how many tokens each expert receives. If expert j should get k/N of the tokens (a fair share) but instead gets k/2 (because the router is collapsing), the penalty detects it and adds pain to the training goal. The router now faces a trade-off: boost performance (pick the genuinely best experts) or spread tokens around (stay safer). The router learns the balance: if it can prove this input truly needs expert 3, it routes there; if it tries to over-specialize out of laziness, the penalty hits. This is a safety guardrail: it does not force uniform routing (the term adds up, it is not a hard rule), but collapse becomes so costly that the router must diversify. Entropy (spreadness) of the routing shares measures this health: high entropy means well-spread, low entropy means collapsed.

Capacity decoupled from active compute cost

Parameters ∝ N, FLOPs per token ∝ k, N ≫ k
This is the payoff. A normal model with N parameters must run all N for every token, so compute per token is Θ(N). An MoE with N total experts, each the same size, runs k per token. The compute per token is Θ(k)—which does not grow as you add experts. Why is this possible? Because running an expert is not where the cost lives—which experts you run is where it matters. Sparse routing flips the scaling: you pay a small cost to talk to all experts (send the token, get answers back), but you compute only what you need. For huge models, this small cost of talking is tiny compared to the savings from skipping most expert compute, so you win. The cost you pay instead: memory (all experts must fit somewhere) and training compute (across all tokens in all training, you compute more than a model with fewer experts—but per token you compute less, so you can train on more tokens in the same compute budget).

Perplexity of routing as a health readout

Perp_router = exp(−Σᵢ gᵢ(x) log gᵢ(x)) = 2^entropy
To check if your router is working or collapsing, compute the perplexity of the routing shares per token: average entropy (spreadness) of g(x) over a batch. Perplexity is a number: if it equals k (e.g., 2 when you route to top-2 experts), the router is nicely spread—each token uses roughly k distinct experts. If perplexity drops to 1.1 or 1.2, the router is collapsing, picking one expert for almost everything. If it climbs above k, the router is spreading tokens too thin or is unsure—a signal that you might have too many experts or the task is too noisy. Perplexity is not the full story (it does not check if the right experts are chosen—it just measures spreadness), but it is the first gauge: a sudden drop in perplexity mid-training is your alarm to tune the balancing loss or restart the router.

The approaches, as variations on the math

The recipe has two tunable knobs. Knob 1: choose k, the number of experts per token. Larger k means less sparsity (more compute), but the router gets clearer signals and less pressure from load-balancing. Knob 2: set the load-balance strength λ. Too low and collapse sneaks in; too high and the router ignores the input and spreads tokens evenly, wasting the expert capacity. Every variant—routing per token vs. per sequence, adding extra losses, dropping experts randomly—is a twist of these knobs and how k is enforced (hard top-k cuts off sharply, soft top-k tapers). A big choice: expert depth. Use shallow experts (feedforward networks only) paired with a shared backbone, or deep experts that replace whole transformer blocks (fewer fit in memory, but each is more capable). Another: load-balance method. The simplest spreads tokens evenly; smarter methods use extra losses that reward using different experts for different data types, or gate-balancing that punishes any single expert's learning signal growing too large. Finally, communication cost. In distributed training, each expert sits on a different machine; tokens must cross the network. Smaller k cuts network traffic; the trade-off is weaker signal per expert, so they specialize less. Top systems often use hybrid design: dense layers at the bottom (cheap to shuffle), sparse MoE in the middle (where capacity matters most), and a small dense layer on top (to coordinate).

A worked numeric example

Suppose four experts have router logits [3,2,0,-1]. Softmax weights are about [0.696,0.256,0.035,0.013]; top-2 routing keeps the first two and skips half the network. The model has four experts of capacity, but this token pays for only two.

2The fragile heart

The through-line. Mixture of experts flips the scaling: instead of compute growing with model size, add as many experts as memory allows and pick them sparsely. The core tension is collapse—without load-balancing, the learned router converges to a useless solution—which reveals that sparse routing is a learned soft choice held accountable by a balancing penalty. The same soft-choice move appears here, directed at picking whole sub-networks. The collapse trap is a pattern that recurs whenever one mechanism learns from one goal with no check on it; MoE's balancing loss is the solution. The payoff: grow your model's capacity far beyond what your per-token compute budget allows, by betting that most tokens need only a few specialists, and that those specialists can learn which. When that bet works, you get unprecedented model size within a fixed training budget.
