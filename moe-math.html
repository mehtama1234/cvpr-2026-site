Mixture of experts — why it works, mathematically

Activate only a few experts per token, so you scale parameters without scaling compute—but only if the gate can learn which experts without collapsing into one.

The problem, as a quantity

A monolithic model with d parameters must run all d of them for every token. To add knowledge, you add d, so a model with twice the capacity costs twice the compute per token. The real problem is subtler: every parameter route, whether it helps or harms the token you are processing, adds to your FLOPs. Some weights are specialists in rare events; running them on common tokens is waste. So the hard problem is: how do you let a model choose a tiny fraction of its weights to activate per token, and learn that choice from the signal alone? A hard choice has no gradient. A soft choice via softmax on all experts reintroduces the compute you tried to escape. You need a learned routing function g(x) that selects a real subset of experts yet remains differentiable—and without vigilance, the router will collapse: always picking the same expert, turning your specialists into a single overworked generalist.

The core ideas — and why they work

Sparse routing via soft top-k gating

y = Σᵢ∈topk gᵢ(x)·Eᵢ(x), g(x) = softmax(router(x)), k ≪ N
A token x arrives; a small neural network (the router) reads it and emits logits, one per expert. Softmax turns them into a probability distribution g(x) over all N experts. But you do not compute all experts—you only forward through the k with the highest probabilities. The output is a weighted sum of those k experts' outputs, using the softmax probabilities as weights. Why does this work? Because softmax is differentiable, the gradient of the loss flows back through g(x) to the router, so the router learns to emit high probability on experts that help reduce loss. Crucially, the choice of which experts is soft (determined by smoothly-varying probabilities) even though the computation is sparse (only k run). You get the gradient signal you need to learn what matters. Same primitive elsewhere: softmax selection (turning a choice into a differentiable weighting) runs the entire attention mechanism, CLIP's image-text matching, and Mixture-of-LoRA's skill router—it is the same move, redirected at different scales.

The routing collapse: one expert hoards all tokens

Collapse: g(x) → [0, …, 0, 1, 0, …, 0] for all x (argmax, entropy → 0)
Left to its own devices, a learned router exhibits a fatal instability. Early in training, one expert (by chance) receives slightly more tokens and improves its loss faster. It becomes more attractive, pulls more tokens toward it, and improves even faster—a positive feedback loop, a rich-get-richer spiral. Within a few steps, the router ceases to explore: it always selects the same expert for every input, ignoring features entirely. The softmax now outputs nearly-zero for all but one expert, entropy collapses to near-zero, and your mixture of N experts has become a single deterministic layer—no capacity gain, no benefit. This is not a training quirk; it is a deep pathology of learned selection under no opposing force. The enemy it defeats: the degeneracy trap that haunts every method that mixes objectives—SSL's mode collapse, VQ-VAE's codebook collapse, slot-attention's duplicate slots, RL's reward hacking, TTA's silent failure—the same underlying story: one objective, one shared mechanism, it finds the collapse.

Load-balancing loss forbids collapse

ℒ_load = λ·Σⱼ(Σᵢ gᵢ(x^(i))_j)² / (k·|batch|), target ≈ k/N per expert
To keep experts alive and diverse, penalize imbalance: measure, over a batch, how many tokens each expert receives. If expert j should receive k/N of the tokens (uniform share) but instead receives k/2 (because the router is collapsing), the load-balance loss detects it and adds a penalty to the objective. The router now faces a pressure: boost the loss directly (favor the good experts) or stay safe and spread tokens evenly. The balance point is learned: a router that can credibly argue this input genuinely needs expert 3 will route to it; a router that tries to over-specialize because it is lazy gets slapped by the load-balance term. This is a safety ratchet: it does not force uniform routing (the term is additive, not a hard constraint), but it makes collapse so costly that the router must diversify or die. The healthiness of this balance is measured by entropy or perplexity of the routing distribution—high entropy means well-spread, low entropy means collapsed.

Capacity decoupled from active compute cost

Parameters ∝ N, FLOPs per token ∝ k, N ≫ k
This is the payoff. A dense model with N parameters must run all N for every token, so FLOPs per token is Θ(N). An MoE with N total experts, each the same size, routes to k per token. The FLOPs per token are Θ(k)—independent of how many experts you add. Why is this possible? Because a linear operation (expert computation) is not the bottleneck—which experts you run is. Sparse routing inverts the scaling: you pay the communication cost to talk to all experts (broadcast the input, receive outputs) but compute only what matters. For very large models, the communication cost is small relative to the compute savings, so you win. The risk: you must pay in memory (all experts must live somewhere) and in total training FLOPs (across all tokens, you still do more work to train a 100-expert model than a 10-expert one—but you do it with smaller per-token cost, hence you can train on more tokens in the same compute budget).

Perplexity of routing as a health readout

Perp_router = exp(−Σᵢ gᵢ(x) log gᵢ(x)) = 2^entropy
To monitor whether your router is live or collapsing, compute the perplexity of the routing distribution per token: average entropy of g(x) over a batch or eval set. If perplexity is k (e.g., 2 when you route to top-2 experts), the router is reasonably spread—each token routes to roughly k effective experts. If perplexity drops to 1.1 or 1.2, the router is collapsing, picking one expert for almost everything. If it climbs above k, the router is spreading tokens too thinly or is uncertain—a signal that your expert count may be too high or your task boundary too noisy. Perplexity is not the full story (it misses whether the right experts are chosen—entropy is an information-theoretic proxy, not a correctness measure), but it is the first diagnostic: a sharp drop in perplexity in the middle of training is your cue to check the load-balance loss tuning or re-initialize the router.

The approaches, as variations on the math

The recipe has two tunable axes. Axis 1: choose k, the number of experts per token. Larger k is less sparse (more compute), but richer routing signals and less pressure on the load-balance loss. Axis 2: set the load-balance coefficient λ. Too small and collapse sneaks in; too large and the router ignores input features and routes uniformly, wasting the expert capacity. Every variant—per-token vs. per-sequence routing, auxiliary losses, expert dropout, meta-routing (routing routers)—is a tweak of these two axes and the details of how k is enforced (hard top-k vs. soft top-k with a temperature). A key design choice: expert hierarchy. Use shallow experts (pure feedforward nets) paired with a shared base model, or deep experts that replace whole transformer blocks (fewer experts fit in memory, but each is more powerful). Another: load-balance strategy. The simple approach spreads tokens uniformly; better methods use auxiliary losses that reward diversity of expert usage across different data subsets, or gate-balancing that penalizes any single expert's gradient norm growing too large. Finally, communication overhead. In distributed training, each expert lives on a different device; tokens must be routed across the network. Reducing k cuts communication; the trade-off is lower per-expert signal, so expert specialization is weaker. The state-of-the-art often uses hybrid architectures: dense layers at the bottom (cheaper to shuffle around), sparse MoE in the middle (where the capacity is greatest), and a small dense layer at the top (to coordinate).

1Keep the senses separate
Score(token) → Σ_i(soft_modality_weight_i · expert_i); route based on how text-like or image-like token appears, without hard assignment
Soft gating preserves gradient flow to each expert while nudging them toward modality specialization. Unlike hard discretization, this lets the router learn what balance works best per token without commitment penalty, and experts naturally cluster around their strongest modalities as a learned side effect.
Soft Modality-Guided Expert Specialization in MoE-VLMs — Soft modal scoring assigns each token a text/image affinity score, steering expert selection without hard routing rules.
G2VLM: Geometry Grounded Vision Language Model with Unified 3D Reconstruction — Dual pathways (what+where) split visual features before expert routing, encoding human visual hierarchy into MoE branching.
MOON2.0: Dynamic Modality-balanced Multimodal Representation Learning — Modality-driven gating weights experts by presence-of-modality indicator, balancing load across image/text/audio via first-order modality statistics.
OneCAT: Decoder-Only Auto-Regressive Model for Unified Understanding — Single decoder processes raw pixels as tokens via lightweight projection, routing each token position to the same expert set regardless of modality.
2The fragile heart
Stabilize router via eigenbasis reparameterization or dual-model guidance: expert_i = U_i · eigenvector_i (orthonormal basis per expert) OR gate_output = blend(student_affinity, teacher_guidance) + drift_penalty
Router collapse happens when gates converge to a single expert; orthonormal reparam spreads signal across clean, non-overlapping dimensions so diversity is baked into parameter space. Teacher guidance or drift-aware penalties add external pressure that prevents premature convergence by rewarding honest disagreement about which expert fits best.
ERMoE: Eigen-Reparameterized Mixture-of-Experts for Stable Routing — Each expert resides in its own learned orthonormal basis, making expert overlap zero and routing collapse harder via orthogonality constraint.
Teacher-Guided Routing for Sparse Vision Mixture-of-Experts — Dense teacher model supplies global routing guidance to sparse student, preventing local gate convergence via distillation auxiliary loss.
MoE-GRPO: Optimizing Mixture-of-Experts via Reinforcement Learning — Expert selection becomes a sequential MDP solved by Group Relative Policy Optimization, replacing fixed gates with learned routing policies.
On Token's Dilemma: Dynamic MoE with Drift-Aware Token Assignment — Relative-difference measure between top-k expert affinities detects ambiguous tokens, dynamically expanding capacity when uncertainty is high.
3Keep every expert working, cheaply
Recover expert usage from dense model trace: cluster(dense_activations) → initialize sparse experts from clusters; OR dispatch(token, layer) → can_skip(layer, modality) = analyze_expert_usage_pattern(train_data)
Dense-to-sparse distillation reuses knowledge that the dense model already discovered about input structure, so experts start already specialized instead of learning from scratch. Speculative skipping (per-layer per-modality) reads the actual activation pattern and removes dead capacity at inference, trading zero training cost for throughput.
Enhancing Mixture-of-Experts Specialization via Cluster-Aware Upcycling — Dense model activations are clustered first, then experts are initialized as cluster centroids rather than blind dense clones.
VidPrism: Heterogeneous Mixture of Experts for Image-to-Video Transfer — Each expert is permanently bound to a temporal window (frame 0, frame 1, ...), making heterogeneous expert specialization by design.
MoDES: Accelerating Mixture-of-Experts Multimodal Large Language Model — Per-layer, per-modality expert pruning mask identifies safe-to-skip experts at inference via oracle training-free scoring.
OneSparse: A Unified Framework for Sparse Activation Layers in Vision — Sparse routing (dispatch, process, combine) unifies MoE and other sparse layers under a common three-step operator composition.
4One model, many jobs
Router gate conditioned on task_id: gate(token, task) = softmax(W_task · token_embedding); dispatch expert to subtask via task-aware affinity instead of task-agnostic scoring
Task-conditioning lets a single MoE pool solve multiple downstream problems by having the gate itself become task-aware, so the same expert can specialize to different roles depending on which task is asked. Frequency-domain routing (spectral components) achieves similar multiplexing by splitting input structure orthogonally across spectral channels.
MoRE: 3D Visual Geometry Reconstruction Meets Mixture-of-Experts — Dense 3D backbone feed-forward layers are replaced with expert blocks, letting task-specific geometry experts co-inhabit one model.
UETrack: A Unified and Efficient Framework for Single Object Tracking — Token-pooling router aggregates multimodal features into expert selection, routing pooled embeddings rather than raw tokens.
Spectral Mixture-of-Experts for Continual Learning — Router decomposes input along frequency spectrum, assigning each spectral band to an expert, enabling spectral-domain task separation.
TAG-MoE: Task-Aware Gating for Unified Generative Mixture-of-Experts — Task embedding concatenated into routing computation makes gate aware of downstream objective, enabling task-conditional expert selection.
5Stairs and gravel without forgetting
Expert_i specializes on terrain_i via MoE policy: π(action | state, expert_i) = learned_gait_i; selector picks expert from state→terrain classifier or from multi-expert teacher
Terrain-specific experts inside a reinforcement-learning policy avoid forgetting by keeping each behavior isolated in its own parameter island; the router learns which gait solves which ground type via experience, and skill transfer happens through shared state encoder. Multi-skill switching stays stable because each expert trains independently on its narrow domain.
MoE-Loco: Mixture of Experts for Multitask Locomotion — RL policy network embeds MoE block such that each expert learns terrain-specific gaits, specialization emerges from environment interaction.
VMTS: Vision-Assisted Teacher-Student Reinforcement Learning for Multi-Terrain Locomotion — Separate terrain-specific teacher policy for each ground type, router selects teacher via visual terrain classifier signal.
BeeTLe: Blind Terrain-aware Learned Locomotion — Multi-expert policy stores disjoint gaits per terrain type, router selects gait without vision by inferring ground contact dynamics.
MOVE: Multi-Skill Omnidirectional Legged Locomotion With Limited View — End-to-end RL policy branches to skill-specific experts (climbing, leaping, crawl, stair), skill selector outputs routing logits.
6Skills and scenarios that stop fighting
LoRA adapter as sparse expert: π_total = Σ_k(gate_k · (base_policy + lora_k)); multi-head skill transformer: head_i outputs primitive_i; causal planner fuses expert predictions via sparse gating
LoRA adapters store distinct behaviors as low-rank perturbations around a shared base, so skills are parameter-efficient and composable without gradient conflict. Multi-head and causal fusion allow long-horizon tasks to decompose across both skill type (which motion primitive) and state sequencing (which plan step), with the gate orchestrating both simultaneously.
MoRE: Unlocking Scalability in Reinforcement Learning for Quadruped Visualization — LoRA adapters inside dense multimodal LM act as sparse-gated mixture, scaling RL without dense model parameter blowup.
MuST: Multi-Head Skill Transformer for Long-Horizon Dexterous Manipulation — Parallel transformer heads, one per motion primitive, keep skill learning separate, combining head outputs additively.
Generalizing Motion Planners with Mixture of Experts for Autonomous Driving — Decoder planner backbone replaced with mixture of expert decoders, each expert predicts trajectories for a scenario cluster.
Expert-Enhanced Masked Point Modeling for Point Cloud Self-Supervised Learning — Sparse MoE token router after each backbone block assigns point tokens to domain-specific experts via point-wise routing scores.
The through-line. Mixture of experts inverts the scaling relationship: instead of FLOPs growing with parameter count, add as many experts as memory allows and route sparsely. The core tension is the routing collapse—without load-balancing, the learned selection function converges to a trivial solution—which reveals that sparse routing is a learned soft-argmax held accountable by a balancing loss. The same softmax-selection move that powers attention and skill-routing shows up here, directed at choosing whole sub-networks instead of tokens or adapters. And the degeneracy trap—one objective, one mechanism, it finds the collapse—is a shadow that haunts every multiplexing method in deep learning; MoE's load-balance loss is the field's answer to it. The payoff: scale your model's capacity far beyond what your per-token compute budget permits, by betting that most tokens need only a few specialists, and that those specialists can learn which. When that bet pays off, you get unprecedented model size within a fixed training budget.
