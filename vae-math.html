Variational autoencoders — why it works, mathematically

You want to squeeze complicated pictures into a compact, tidy code—then pull them back out. But training stumbles: you can't learn by randomly guessing the code, and the code space wants to collapse. A VAE routes the randomness through the network itself and trains against a bound instead of the impossible.

The problem, as a quantity

Suppose you want a machine that understands pictures. It should be able to take a messy real photograph and compress it—force all its information into a short list of numbers, far shorter than the pixel count. Then, it should be able to do the opposite: take that short code and rebuild a picture from it. That sounds useful, like a private language the network invents for pictures.

The catch: for the machine to generate new pictures on its own (feeding it random codes and hoping for plausible output), the code space needs structure. Codes should cluster in a smooth, tidy region, and nearby codes should decode to similar-looking pictures. During training, though, two things go wrong. First, if you just sample random codes from some guessed spread, the network can't learn from the randomness—the blame can't be traced back through a random number. Second, if you only train the compression and rebuild, the network will ignore the code space entirely, dumping all information into an unstructured mess, making generation impossible.

The core ideas — and why they work

Squeeze into a compact code, then rebuild from it

x → z → x̂: encode q(z|x), decode p(x|z), dim(z) ≪ dim(x)
The core idea is radical simplicity: take your input (a picture, say), push it through a compressor network that outputs a short code—that is your compressed representation. Then push that code through a decoder network that tries to rebuild the input from scratch. Call the compressor the 'encoder' and the decoder the 'decoder.' The code is much shorter than the input, so the network is forced to throw away details it doesn't need. You measure how well the decoder did by checking how close the rebuilt output is to the original. The whole machine—encoder plus decoder together—learns to compress and decompress anything you throw at it. The trick is that the code size is fixed and small, so bottleneck forces the encoder to distill the important structure.

You can't learn through random sampling, so re-route the randomness

z = μ(x) + σ(x)·ε, ε ~ N(0,I) (reparameterization)
Here is the hard part: you want the network to adjust its internal numbers based on random samples from the code, but the blame cannot be traced back through randomness—you cannot compute a slope through a coin flip. The solution is to reroute the randomness. Instead of sampling the code directly, the encoder outputs two things: a center (call it μ, the mean) and a spread (call it σ, the standard deviation). Then, outside the network, you generate a random list of noise values from a standard bell curve (that is ε). You build the actual code by mixing them: code = center + spread × noise. The blame traces back through the center and spread smoothly. The randomness itself is outside the network, so it never blocks the slope signal. This is reparameterization: you rerouted the source of randomness so the network can learn.

Train against a bound you can actually compute

L = E_q[log p(x|z)] − KL(q(z|x) ‖ p(z)) (the evidence lower bound)
Training against a loss function (a measure of wrongness) is straightforward: make the rebuilt output as close to the input as possible. But that is only half the problem. You also need the code space to be smooth and structured—you want nearby codes to decode to similar outputs, and codes should cluster in a sensible region. The solution is to train against a lower bound on a quantity called the 'evidence,' which wraps both goals into one number. The bound has two parts: first, how well does the rebuilt output match the input? (call this the reconstruction term). Second, how close is the learned code spread to a tidy, standard bell curve? (call this the KL term, which measures mismatch from the ideal). By maximizing this bound—equivalently, minimizing its negative—you push the network to compress faithfully and keep the code space tidy. You never need to sample from the code spread itself during training; the bound gives you a concrete target that works.

A tug-of-war: rebuild faithfully vs. keep the code space tidy

reconstruction term vs. KL term (a β dial sets the balance)
The bound has a knob attached. The reconstruction term pulls the network toward rebuilding inputs perfectly. The KL term pulls the network toward matching a standard bell curve. These two forces fight: pack information densely into the code and you wreck the bell curve shape; smooth out the code space and you lose precision in the output. The knob is a scaling factor (often called β) that sets which goal matters more. Turn β up and the network obsesses over a tidy code space, accepting blurry rebuilds. Turn β down and the network rebuilds sharply but lets the code space sprawl. The VAE is doing a deliberate trade-off: Do you want a better generator, or a better compressor? The dial lets you answer that question for your task.

The approaches, as variations on the math

The same autoencoder machinery can be tuned several ways. The encoder architecture—how many layers, how wide, which nonlinearities—shapes how much information flows into the code. The decoder architecture—the mirror question for rebuild—shapes how faithfully the network can reconstruct. The code size sets how much compression is forced: shrink it and the network distills harder, but rebuilds suffer. The β dial shifts the balance between reconstruction fidelity and code-space tidiness. The choice of prior (the standard bell curve, or something else) changes the shape the network is pushed toward. The thread never changes: an encoder forces information through a bottleneck, a decoder tries to rebuild it, reparameterization keeps randomness outside the backward pass, and a lower bound on evidence ties reconstruction and prior-matching into one goal.

The through-line. The core problem is learning a compressed representation of high-dimensional data, while also building a probability model over that code space so you can generate new examples. Naive approaches fail: you cannot trace the blame back through random sampling, and an unstructured code space makes generation useless. A VAE solves this by rerouting randomness through the encoder's outputs (mean and spread) so the network can learn them, and by training against a lower bound on evidence instead of an impossible direct objective.

Two plain ideas carry it: reparameterization keeps the blame flowing by moving the source of randomness outside the network, and a tractable lower bound wraps the dual goals—faithful compression and tidy code space—into a single loss function the network can optimize.
