Mixture of LoRA — why it works, mathematically

You have one big pretrained model and want to teach it many separate skills — French, legal writing, medical answers — cheaply, keeping each skill clean and combinable, without a costly full retraining for every one. This is how each skill becomes a tiny add-on patch, and a chooser blends the right patches per input.

Plain-English big picture

What this is really about

A LoRA adapter is a small change to a large model. A mixture of LoRA adapters keeps several small skills and chooses how much of each skill to use for the current case.

Where topology and shape enter

In topology terms, each adapter can be seen as bending the model in a small direction. A mixture lets the model move along several skill directions while staying near the original model instead of jumping to a completely new one.

Where the same idea appears elsewhere

It appears in personalization, domain tuning, image generation, language models, and multi-task systems.

Why Mixture of LoRA is worth learning

It matters because many users need custom behavior, but copying and retraining a huge model for every case is wasteful.

The key turn — the principle at work

The stuck point. A full model update is huge, but most tasks only need a small change in behavior. Storing a separate full model for each task wastes memory and makes switching expensive.

The mathematical move. The principle is low-rank change. LoRA writes the task update as the product of two small matrices, so the change can only move in a few learned directions. A mixture adds routing: different inputs combine different small updates.

What changes. Adaptation stops meaning 'copy and rewrite the whole model.' It becomes 'learn a few useful change directions and choose among them.' The risk is that too few directions miss the task, while too many lose the point of compression.

The problem, as a quantity

A big pretrained model is expensive to retrain — it holds billions of adjustable numbers, and adjusting all of them to add one narrow skill is enormously costly. You want to teach it many skills without paying that price each time, and you want the skills to stay clean: adding a new one should not blur or overwrite the old ones, and you should be able to mix them as a task demands.

So the problem has three parts. Make each new skill cheap to learn and cheap to run. Let the model decide, per input, which skills to bring to bear. And add skills side by side so they accumulate rather than collide. The pieces that follow solve each part in turn, and together they turn one frozen base model into a growing library of combinable skills.

The core ideas — and why they work

A new skill is a small patch, not a whole new model

ΔW = B·A, A ∈ ℝ^{r×d}, B ∈ ℝ^{d×r}, r ≪ d ⇒ 2dr trainable numbers instead of d²
Teaching a big model a new skill by retraining all of its numbers is enormously expensive — there are billions of them. The key observation is that a single narrow skill does not need to touch all of them: the change a skill makes to the model is simple, and can be captured by a thin patch built from far fewer numbers.

Instead of adjusting a giant square of numbers, you adjust two skinny strips whose combination stands in for that square — a few thousand numbers rather than billions. So a skill becomes a small, cheap patch you train while the huge base model sits completely frozen. This is what makes it affordable to teach many skills: each one is tiny, so a library of dozens of them costs a fraction of retraining the base even once.

The patch folds in, so it costs nothing to run

(W + B·A)·h = W·h + B·A·h — an exact identity; at test time fold B·A into W, extra cost → 0
A useful property of the patch: because it simply adds to what the base model already computes, you can merge it straight into the base model's numbers before running.

Once merged, the patched model is exactly one model again — no extra layers, no slowdown; the patch's running cost drops to nothing after it is folded in. And when you are done, you can un-fold it and the base is untouched, ready for a different patch. So a skill is not only cheap to train, it is free to run and leaves no permanent mark. You can carry a whole library of skill patches and snap whichever one you need onto the same untouched base, at no ongoing cost.

Which skill? Let a chooser blend the right ones per input

h ↦ Σᵢ gᵢ(x)·BᵢAᵢ·h, g(x) = softmax(router(x)), gᵢ ≥ 0, Σᵢ gᵢ = 1
With a library of skill patches, which one should handle a given input? Rather than pick by hand, add a small chooser that looks at each input and decides how much of each patch to apply — turning its relevance scores into shares that add up to 1, then blending the patches by those shares.

A legal question leans on the legal patch, a French sentence on the French patch, and something in between can draw on both at once. Because the blend is smooth — a tiny change in the scores makes a tiny change in the mix — the chooser can be trained by ordinary small nudges to route each input to the skills that help it. This is exactly the mixture-of-experts idea, applied at the scale of cheap skill patches instead of whole networks.

New skills add alongside old ones, never on top

W_frozen + Σᵢ gᵢ(x)·BᵢAᵢ — a new skill is a new summand; the base is never rewritten
A big danger in teaching a model new things one after another is that each new lesson overwrites the last — learn medicine and it forgets law. This design sidesteps that entirely.

The base model stays frozen and untouched, and every skill is a separate patch added alongside the others, never written on top of them. Adding a new skill just means training one more patch and dropping it into the library — the existing skills are literally the same numbers they were, undisturbed. So skills accumulate cleanly instead of colliding: no forgetting, no interference. And because each one is its own independent piece, you can add, remove, or recombine them freely, mixing exactly the skills a given job needs.

The approaches, as variations on the math

Designs here turn a few dials on the same idea.

How thin the patch is. Fewer numbers per patch is cheaper but can capture only simpler skills; a slightly wider patch holds more at more cost. How the chooser decides. Per input, per piece of the input, or by a fixed rule — and how many patches it blends at once. How patches combine. Softly blended by the chooser, or selected one at a time, or stacked so several always apply. What a patch is trained on. A language, a domain, a style, or a specific robot skill — each a separate cheap add-on. The thread never changes: a skill is a cheap add-on patch, not a rewrite of the model, and many such patches can be routed and combined without ever colliding.

A worked numeric example

A dense 4096×4096 update has 16,777,216 numbers. A LoRA with rank 8 stores 2·4096·8=65,536 numbers, about 256× smaller. If a gate blends three such adapters with weights [0.7,0.2,0.1], the skill update is a weighted sum of tiny bends rather than a new full model.

1Meet the world the giant never saw
ΔW = B·A applied to frozen model; task-specific patches (B_task, A_task) inject domain knowledge without rewriting base
A pretrained foundation model learns broad patterns from huge amounts of data. Freezing the backbone — locking its numbers in place — forces learning into low-rank space: a small, controlled set of dimensions. So each new domain is compressed into its essential change: only the few directions where it actually differs from the broad base. These patches are additive residuals — they layer new knowledge on top of the frozen structure, preventing the erasure of old skills. The model keeps what it learned before and adds only what is new.
These four papers all ask how to teach a frozen model new domains without erasing what it already knows. One paper adds independent low-rank patches per domain; another uses a learned gate to route samples to the right patch; a third enforces special structure on the patch matrices to preserve distance; a fourth keeps LoRA separate from the main path and only applies it as a small residual correction.

2Two ideas in one picture
Separate rank-r LoRA modules per concept (content B_c·A_c, style B_s·A_s); compose as ΔW = B_c·A_c + B_s·A_s
Content (what something is about) and style (how it looks) are independent axes. By training independent low-rank modules for each, you isolate their roles — each expert learns one semantic axis and only that axis. Rank-constrained composition keeps modules specialized and prevents entanglement, so they recombine cleanly across tasks. You can swap one without breaking the other.
These four papers all split the job into two separate specialized paths running in parallel. One does content separately from style; another fuses different style experts via special geometry; a third applies LoRA to different layers for different jobs; the last enforces two losses to make each LoRA capture a distinct axis.

3A committee inside one model
Router gate g(x) selects expert subset; ΔW(x) = Σ g_i(x)·(B_i·A_i), sparse activation only when needed
Not all samples need all experts. A learned gate — a tiny network — reads the input and picks which experts matter. One sample activates few experts, another activates different ones. Sparsity reduces computation; routing lets each expert focus on its own subproblem without interference from others. The gate learns 'this input needs expert 1, not expert 2'; a different input takes a different path.
These four papers all build a committee where different experts specialize in different things. One has multiple geometry experts that switch in parallel; another cascades two gates for vision and action; a third has patch-specific experts for spotting anomalies; the last splits policy behaviors across expert skills in a robot controller.

4Learn more without forgetting or fighting
Frozen base + per-task LoRA modules (B_i·A_i per task i); no base rewrite, no gradient conflict via domain routing g_d(x)
As tasks arrive sequentially, adding new low-rank modules keeps the frozen backbone clean — it never changes. A domain router assigns each sample to its task's module without contaminating shared structure. Learning updates stay confined to per-task experts, so training on task N does not clobber task 1. The base is universal, and each task has its own small tweak that lives in its own low-rank space.
These four papers all face the same challenge: when you add new tasks sequentially, the model must not erase old learning. One uses dual gradients to keep new updates orthogonal; another penalizes drift from the original routing; a third splits the signal by frequency; the last scales each expert's contribution without letting it rewrite anything.

5Combine specialists after training
Merge disjoint LoRAs via null-space geometry; if ker(A_i) ⊥ ker(A_j), then ΔW = B_i·A_i + B_j·A_j remains optimal
Each trained expert occupies a low-dimensional subspace in the weight space — the set of directions it actually uses. If two experts' subspaces are orthogonal (perpendicular in high-dimensional space; their unused directions do not overlap), their contributions combine without conflict. Merging projects all experts into a single low-rank update; subspace structure guarantees recovery of all learned behaviors. You can take two independent experts and fuse them into one without losing anything.
These four papers all ask: after each expert is trained, how do you merge them into one? One uses aligned projection; another preserves the unused subspaces; a third finds a Pareto-optimal combination; the last compresses task info and uses freed-up space for constraints.

6Make the router trustworthy
Reparameterize gate via eigenvectors of task covariance; g(x) = softmax(Q·E·c(x)), Q eigenbasis avoids mode collapse
Learned gating alone is brittle — the learning process concentrates weight on a few favorite modes, making the router ignore other specialists. The fix is tying gates to data geometry: use eigenvectors (the main independent directions in which data varies) of task statistics. Eigenspace parameterization anchors routing to real structure, stabilizes sparse activation, and forces honest specialization. The router learns from the actual shape of the data, not just trial and error.
These three papers all try to fix the same problem: learned routing often collapses, ignoring specialists and using only one expert. One reparameterizes the gate using eigenvectors; another starts by mimicking a teacher; the third seeds each expert toward different regions before training.

7Mixture-of-LoRA proper — the keystones
Σ g_i(x)·(B_i·A_i) where each expert i is fully low-rank and gate g(x) is learned; dynamic routing respects rank constraint across all experts
True Mixture-of-LoRA merges three layers: a shared frozen base, a dynamic gate that learns routing patterns from data, and a set of learned low-rank experts. Each expert B_i·A_i is intrinsically small (rank r ≪ d), so adding experts is cheap. The gate learns which expert matters for which input, making the whole system both parameter-efficient and task-adaptive. You get many skills living in small spaces, coexisting side by side, and the model learns how to use them.
The through-line. The core idea is that a narrow skill is a small, cheap patch — a few thousand numbers, not billions — that adds onto a frozen base model, folds in at no running cost, and leaves the base untouched. A small chooser blends the right patches per input, which is exactly the mixture-of-experts idea at the scale of skill patches; and because every skill is a separate added patch, skills accumulate without ever overwriting one another. Two plain ideas carry it: a skill is a cheap add-on patch rather than a rewrite of the model, and many such patches can be routed and combined freely without colliding.
