DETR — detection as guessing a set, all at once

For years, finding objects in an image meant a pipeline of hand-designed parts: scan a grid of candidate boxes, score each, then run a clean-up pass to delete the near-duplicates. DETR threw all of that out for one clean idea borrowed from language models: hand the image to a transformer and let a fixed set of learnable queries each emit one object — the whole set at once, no grid, no clean-up. This page is the plain story of that idea — the one-to-one matching at its heart, the slow-to-learn cost the run makes you feel, and how the same idea became the template for half of modern vision.

Mathematical core

Hidden quantity. The page is really about estimating the set of objects and the assignment between predictions and real instances.

Evidence. The model sees object queries, image features, boxes, masks, classes, and matching loss.

Rule. The fundamental rule is to predict a set directly and use one-to-one matching so each object is claimed once.

Failure test. Queries can duplicate one object, miss small instances, or bind a confident prediction to the wrong evidence.

1 · The problem — find every object, exactly once

Point at a photo and list what is in it, with a box around each thing. The hard part is not any single object; it is that you do not know how many there are, and you must find each one exactly once. The classic recipe proposes thousands of candidate boxes on a grid, scores them all, and then runs a hand-tuned de-duplication step to collapse the pile of overlapping guesses down to one box per object. It works, but it is a stack of heuristics — the grid of anchors, the thresholds, the clean-up pass — each needing careful tuning.

The problem, stated once: report every object in an image exactly once, without knowing the count in advance — and ideally without a tower of hand-designed candidate-boxes and de-duplication rules.

2 · The reframe — predict a whole set, matched one-to-one

The idea: stop scoring a grid; predict a fixed-size set of objects directly. Give the model a fixed number of object queries — think of them as a row of empty slots. Feed the image through a transformer; each query attends to the picture and outputs one object (a box + label) or the special answer nothing. To train it, you need to say which prediction should match which real object — so you find the one-to-one pairing that best lines predictions up with ground-truth objects (the Hungarian match), and push each query toward its assigned object. That one-to-one rule is the whole trick: because each object can be claimed by only one query, the model is forced not to emit duplicates — so the de-duplication pass simply disappears.
match = argmin_(one-to-one) Σ cost(prediction_i , object_(match(i))) # Hungarian assignment loss = Σ [ class + box error between each query and its matched object ]     # N queries in, a set of objects out, no anchors, no NMS

It is a beautiful simplification — detection becomes one clean set-prediction problem, end to end. It also buys one notorious headache, and the run makes you feel it.

3 · Seen on a real run — the pain and the payoff

1 · It works — but it is famously slow to learn

We built a tiny DETR: 10 object queries, a small transformer decoder, Hungarian one-to-one matching, trained on little scenes of coloured shapes. It ends up good — 0.79 precision at 0.79 recall. But watch how it gets there:

For the first several epochs it is almost useless — precision 0.037 at epoch 1, barely above nothing. The queries are all fighting over the same objects and the one-to-one matching keeps reshuffling who is responsible for what. Then, around epoch 8, it snaps: the queries divide up the work and precision leaps to 0.55. This slow start is the single most famous complaint about DETR, and a whole line of research exists just to fix it.

2 · What the queries learned — they tiled the image

Why did it snap? Because the 10 queries specialized. Each circle marks where one query learned to look. They started identical and random; training spread them out until each one covers a different region of the image — a division of labour the model discovered on its own. The slow phase is the queries negotiating this map; the jump is when they finish.

3 · One read of the scene, every object at once

true object    a query's prediction

After training, the model reads the scene once and emits all objects in parallel — each landed prediction is one query that found one object. No sliding window, no anchor grid, no de-duplication pass; the one-to-one matching taught each query to claim a different object.

4 · Why it matters — the template that ate vision

DETR's win was removing the hand-built machinery: no anchor grid to tune, no non-maximum-suppression to tune, just a set predicted end-to-end and trained by matching. That template turned out to be almost universal — swap what a query stands for and the exact same machinery does instance segmentation, panoptic segmentation, pose, tracking, even counting and grounding (the papers are full of it). The price is the slow convergence you just watched, plus a fixed query budget — so most follow-up work is about making the queries specialize faster (better matching, denoising, deformable attention) while keeping the clean end-to-end set-prediction frame.

5 · The surprise — a fixed set of slots to act on

In vision, a query returns a box to draw. On a robot, that same fixed set of object slots is a fixed set of things to act on — and the end-to-end, no-clean-up pipeline is exactly what a real-time on-board system wants. Even better: because the objects are just a set of query-vectors, two robots can share theirs — one vehicle's object queries fuse with another's to see around a corner neither could alone.

Same set, shared and acted on. Cooperative-perception systems literally pass object queries between agents and match them into one set; drones and vehicles run DETR-style detectors on-board precisely because there is no anchor-tuning or NMS pass to babysit. Vision predicts a set to label; a robot predicts a set to fuse and act on. The in-the-wild page lays out both sides.
