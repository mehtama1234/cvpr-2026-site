State-space models / Mamba — why it works, mathematically

To answer a question at the end of a long book you must have carried the important bits forward as you read. This is how a model walks through a very long sequence carrying a fixed-size running summary — and how it learns to decide what is worth keeping.

Plain-English big picture

What this is really about

Mamba and state-space models keep a compact memory that changes over time. Instead of comparing every token to every other token, the model carries a running state and decides what to remember or forget.

Where topology and shape enter

For topology, this is useful when structure unfolds as a scan or sequence: tracing a boundary, following a vessel, walking along a mesh, or reading frames in a video. The memory must preserve the connected story without storing everything.

Where the same idea appears elsewhere

It appears in language, video, audio, sensors, robotics, and long document processing.

Why State-space models / Mamba is worth learning

It matters because long inputs are expensive. A good memory lets a model handle long streams without all-pairs comparison.

The problem, as a quantity

A model reading a long sequence — a paragraph, an hour of sensor readings, a whole book — has a memory problem. To use something from far back it must have kept it somehow. One way is to let every piece look back at every earlier piece, but the bookkeeping for that grows with the square of the length, and the record of the past keeps growing without bound, so it eventually becomes impossible on very long or never-ending inputs.

The alternative is to carry a running summary: a fixed amount of memory that you update as each new piece arrives, the way you hold the gist of a book in your head rather than re-reading every page. That keeps the cost per step flat no matter how long the sequence gets. But it raises its own hard question: with only a fixed amount of room, what do you keep and what do you let fade? A summary that forgets on a fixed schedule will drop the one crucial clue and clutter itself with filler. The real problem is to carry a small fixed-size memory through an arbitrarily long sequence and still be smart about what goes into it.

The core ideas — and why they work

Carry a running summary instead of re-reading everything

h_t = Ā·h_{t−1} + B̄·x_t, y_t = C·h_t, h_t ∈ ℝ^N, N ≪ L
As the model steps through the sequence one piece at a time, it keeps a running summary — a fixed-size list of numbers, written h_t. At each step it does two small things: fade the old summary a little and fold in the new piece x_t, giving the updated summary; then read off its answer for this step, y_t, from that summary.

The point that makes everything else possible is the size. The summary has a fixed length N no matter how long the sequence L becomes — and N is far smaller than L. So the work at each step never grows, and the model can walk through a sequence of any length while carrying only a constant amount of memory. Anything from far back that still matters has to be held inside those N numbers — which is exactly why the next question, what to keep, decides whether the whole scheme works.

A fixed fading rule is fast but content-blind

If A, B, C are constants: h_t = A·h_{t−1} + B·x_t ⇒ closed-form convolution, but one memory strategy for all inputs
In the simplest version the update rule is the same at every step: the amount the old summary fades and the amount the new piece is folded in are fixed constants, identical for the whole sequence.

That has a real upside. Because the same rule applies everywhere, the whole sequence can be worked out in one sweeping calculation with a fixed repeating pattern, instead of being crawled through one step at a time — which is fast. But it has a matching downside. One fading rule for every input means the model cannot decide on the spot that this piece is important and should be held for a long time, while that one is noise to be dropped immediately. It remembers and forgets on a fixed schedule, blind to what it is actually reading — so a small fixed summary run this way is easily swamped by filler.

Letting the input itself decide what to keep

Mamba: Δ_t, B̄_t, C_t = f(x_t); h_t = exp(Δ_t · A)·h_{t−1} + (B̄_t / Δ_t)·x_t, y_t = C_t·h_t
The fix is to make the fading and folding depend on the current piece. At each step the model looks at the piece and computes, from it, how much of the old summary to keep and how strongly to write the new piece in — the amounts Δ_t, B̄_t, C_t all become quantities read off x_t rather than fixed constants.

Now a surprising, important piece can be written in hard and held for a long stretch, while a run of filler barely disturbs the summary at all. The model has learned what to remember instead of following a fixed schedule — and that content-driven choice is the entire difference. It is what lets a small fixed-size summary punch far above its size, holding onto the few things that matter across a very long sequence. The cost is that the update rule is no longer the same everywhere, so the fast one-sweep shortcut of the fixed-rule version needs a cleverer replacement — which the last idea supplies.

A fixed summary scales to endless length

State size N is fixed; KV cache size is L×D. For L → ∞ or streaming: state-space is O(1) memory, Transformer is O(L).
Put the two styles of memory side by side. This running-summary approach holds the same fixed-size state whether the sequence is a hundred pieces long or a hundred million — its memory is flat, it does not grow at all. The rival approach, which lets every piece compare against every earlier piece, has to keep a record of all the past pieces, so its memory grows in step with the length.

For very long inputs, or streams that never end — a live feed, a book read start to finish — flat memory is the difference between possible and impossible: a growing record eventually will not fit, while a fixed summary runs forever on a constant budget. What you give up is completeness: the summary cannot reach back and inspect an exact earlier piece the way all-pairs comparison can. You are trading that reach for the ability to keep going without limit.

Unrolling the summary so it can be built in parallel

Recurrence h_t = A·h_{t−1} + B·x_t can be reformulated as: h_L = (A^L, A^{L−1}·B·x_1 + A^{L−2}·B·x_2 + ... + B·x_L). Associative ops → O(log L) parallel depth.
Stepping through a sequence one piece at a time is slow on hardware that would rather do many things at once. But the update here is linear — just fade-and-add — and that lets the whole chain be regrouped algebraically. Instead of walking the sequence in a single line, you combine partial summaries over chunks, then combine those, in a tree.

Combining in a tree turns a walk of length L into a stack only about log L layers deep, so the summary for a long sequence is assembled in far fewer sequential rounds — the machine can spread the work out across all its lanes at once. It is the exact same summary you would get by stepping one piece at a time; linearity just lets it be computed in a wide, shallow shape rather than a long, thin one.

The approaches, as variations on the math

Every model of this family turns the same few dials.

Fixed rule versus input-driven rule. The plainest version keeps the fading constant, which is fast but content-blind; the selective version lets each piece set its own keep-and-write amounts, which is what makes a small summary smart. How the summary is computed. The same math can be run as a step-by-step walk (best for a live stream, one piece at a time) or unrolled into a shallow tree (best for training on a whole sequence at once). How big the summary is. A larger fixed state holds more at more cost per step, but the cost never grows with sequence length. Mixing with all-pairs comparison. Some designs alternate summary-carrying layers with occasional every-piece-sees-every-piece layers, buying back a little exact reach where it is worth the cost. The thread never changes: carry a fixed-size memory, and let the input decide what it holds.

A worked numeric example

For a one-dimensional state update h_t=0.8h_{t-1}+x_t, an input from five steps ago is weighted by 0.8^5=0.328. If the learned decay becomes 0.95, the same input still has weight 0.774. The state-space lever is visible in the number: change the decay, and the model changes how long memory survives.

1Which order do I read a 2D image

The through-line. The core move is to carry a fixed-size running summary through a sequence, so the cost per step never grows and the model can run on inputs of any length — trading away the completeness of comparing everything to everything in exchange for flat memory. A fixed fading rule makes that fast but blind to content; letting the input set the rule is what makes the small summary smart, holding exactly the pieces that matter. And because the update is linear, that summary can be built either one step at a time or all at once in a shallow tree. Two plain ideas carry the whole thing: keep a constant-size memory instead of the entire past, and let the input itself decide what that memory keeps.
