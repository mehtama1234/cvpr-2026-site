Object-centric learning — why it works, mathematically

To a computer a photo is just a wall of colored dots. This is how a model, with no one ever telling it what an object is, splits that wall into a few separate things — a cup, a plate, a spoon — on its own.

Plain-English big picture

What this is really about

Slot models try to split a scene into a few object-like containers. Each slot competes to explain part of the image, so the scene becomes a set of pieces.

Where topology and shape enter

Topology matters because objects are not just textures. They have connected regions, parts, holes, and boundaries. A slot should own a coherent piece of the scene, not random pixels scattered everywhere.

Where the same idea appears elsewhere

Slots appear in object discovery, robotics, video, scene generation, and physical reasoning.

Why Object-centric learning is worth learning

It matters because many tasks get easier when the world is represented as objects that can move and interact.

The problem, as a quantity

Show a computer a photo of three fruits on a table and all it receives is a grid of numbers: for every dot in the picture, three numbers saying how red, how green, and how blue that dot is. Nothing in those numbers says 'the apple stops here and the pear starts there.' Yet to do almost anything useful the model has to work that out — dots that belong to the same fruit should be grouped together, dots on different fruits kept apart — and no answer key is provided.

Why is that hard? Two reasons. First, the number of ways to sort the dots into groups is astronomically large: with N dots there are far more possible groupings than anyone could ever check one at a time. Second, a model learns only by making tiny adjustments that lower its mistakes, and for that to work every step has to change smoothly when you nudge it. 'Just decide which group each dot is in' is not smooth — it is a hard yes-or-no choice with no in-between — so the model cannot learn it that way.

The way around this is to give the model a small, fixed number of placeholders — call them slots, where a slot is simply a short list of numbers that will come to stand for one object. Every slot competes for every dot, and the model is trained to repaint the original photo using only what the slots have captured. The competition is what splits the picture into groups; the repainting is what forces those groups to line up with real objects.

The core ideas — and why they work

Turning match scores into shares, so the split can be learned

α_{ki} = exp(q_k · f_i / √d) / Σ_j exp(q_j · f_i / √d), Σ_k α_{ki} = 1 for each dot i
Start with a match score for each slot-and-dot pair. Take slot k's list of numbers and dot i's list of numbers, multiply them together position by position, and add up the results. The score comes out high when the two lists agree — that is, when the slot's description fits what the dot looks like. (Dividing by a fixed number, written √d, only keeps the scores from growing too large; it changes nothing important.)

Now, for one dot at a time, take its match scores against all the slots and convert them into shares: numbers that are all positive and add up to exactly 1. That conversion is what the symbol α_{ki} stands for — 'what fraction of dot i does slot k claim.' Because the shares for a dot must add up to 1, every bit of a dot that one slot gains is a bit some other slot loses. That is the competition, and the competition is what carves the picture into groups.

The reason this particular 'turn scores into shares' step is used, and not some other: it is the one way to make the shares all positive, make them add up to 1, and stay smooth — so the model can keep making tiny nudges to the slots' number-lists until the split comes out right, instead of having to hunt through the astronomically many possible groupings one by one.

Repeating the split a few times sharpens it

s_k^{(t+1)} = GRU(s_k^{(t)}, Σ_i α_{ki}^{(t)} · f_i / Σ_i α_{ki}^{(t)}), t = 1, …, T
After one round of competition the split is still fuzzy. Early on, every slot's number-list looks about the same, so each dot spreads its claim roughly evenly across all the slots and no slot has taken charge of anything.

The fix is to repeat the split, tightening it a little each round. In each round, and for every slot: gather the dots that slot currently claims and take their average appearance, counting each dot in proportion to how strongly the slot claims it — a short summary of 'what the stuff I am winning looks like.' Feed that summary, together with the slot's current number-list, into a small reusable formula (written GRU; it has a handful of adjustable numbers and simply hands back an updated number-list for the slot). Then run the competition again with the updated slots. Do this a few times in a row — T rounds in all.

Repeating sharpens the split because slots that started out alike get pushed apart. When two slots both claim the same dot, the training nudges each slot to fit the dots it is already winning and to back away from the dots the other slot is winning. One round cannot settle that tug-of-war; a few rounds can. More is not automatically better: run it too many times while the repainting pressure is too weak and all the slots drift together into one big blob.

The repaint test forces each slot onto a real object

L = Σ_i ‖ x_i − Σ_k m_{ki} · dec_k(s_k) ‖², where the weights m_{ki} are positive and add up to 1 over the slots k for each dot i
Competition on its own gives the slots no reason to lock onto real objects — two slots could split every dot fifty-fifty forever and never specialize. The repaint test is what forces them to.

Here is the test. Each slot's number-list s_k is handed to a small network — a decoder, written dec_k — that paints back a full little picture: the slot's guess at the piece of the image it is responsible for. A per-dot weight m_{ki} decides how much each slot's painting counts toward each dot (these weights are positive and add up to 1 across the slots, so they share out each dot). You then compare the combined painting to the real photo, penalize the difference, square it, and add that up over every dot. That total, L, is the mistake the model tries to make small.

Why does this force clean objects? If a slot claims a dot but its painting gets that dot's color wrong, the penalty jumps. If two slots share a dot, both of their paintings have to produce the right color from number-lists that each only half-describe the real thing — and neither can. The only way out is for each slot to take a whole, connected, consistent region — an object — paint it well, and leave everything else to the other slots. No one ever labels the objects. The split appears simply because a single connected object is the smallest thing a fixed-size painter can reproduce well without help.

How many slots you allow, and what goes wrong at the extremes

K smaller than the number of objects ⇒ one slot is forced to cover several objects ⇒ the repainting cannot succeed and the penalty stays large; K far larger than the number of objects ⇒ spare slots grab meaningless scraps and never settle
The one setting you choose by hand is K, how many slots there are, and it fixes how much the model can express.

Make K smaller than the number of objects and the competition is forced to cram two objects into one slot. That slot's single number-list now has to repaint two separate regions of the picture at once, which a fixed-size painter simply cannot do, so the penalty stays large and training stalls — or the model quietly gives up on one object.

Make K much larger than the number of objects and the leftover slots have nothing real to take. They grab random scraps of texture or background and never settle down: each spare slot claims some tiny meaningless patch and calls it an object. That is the cheap shortcut to watch for — it lowers the mistake a little without doing the real job.

This is why the setting is useful rather than a nuisance. Too few slots and you can watch the model fail to split the picture; too many and you can watch slots go to waste. The right K is the value where every slot is doing real work and the repainting is accurate — and landing on that value is, in effect, the model discovering how many objects are in the scene, with no one having counted them for it.

The approaches, as variations on the math

Every version of this idea is the same machine with three dials.

Dial one — where the slots start. The original method starts each slot from random numbers. Later methods start the slots from features produced by a separately-trained image reader, so the competition begins from something meaningful instead of pure noise.

Dial two — what the painter has to reproduce. Early models repaint the raw colored dots, which is costly and carries little meaning. Others repaint a compact description of each patch that comes from a pre-trained image reader, which is cheaper and carries more meaning. Video models repaint motion, or the next frame, which forces the slots to stay consistent over time.

Dial three — how you stop the wasted-slot problem. You can occasionally re-randomize spare slots during training, add a small extra penalty that discourages a slot from spreading itself thinly, or simply keep K close to the number of objects you expect. In 3D and robotics settings, each slot's numbers are split so that 'where the object is' and 'what it looks like' are stored separately, which lets a planner point at each object directly. The common thread never changes: slots competing for dots, plus the pressure to repaint, adds up to finding objects with no labels.

A worked numeric example

Say one dot splits its claim across three slots as [0.8, 0.15, 0.05] — it is 80% the first slot's, 15% the second's, 5% the third's. So that dot mostly teaches the first slot what it looks like and only slightly adjusts the other two. Do this for every dot in the picture and the slots end up competing over who owns what. The failure to watch for: one slot slowly grabbing nearly all the claim everywhere, leaving the others with nothing to describe.

1Slots and object discovery
α_k(x) = softmax_k(f_k(x)) across K slots for each pixel x; slots updated each round from the dots they win: u_t = GRU(u_{t-1}, weighted-average of the features they claim)
This is the core loop from the top of the page, seen once more. Each slot works out how well it accounts for every dot, turns those match scores into shares (positive numbers that add up to 1 for each dot), and then updates itself using only the dots it is currently winning. Repeating that update a few times pushes the slots to take charge of separate regions, so the shares stop being a blur and settle into a clean split — roughly one slot per object, with no one ever saying where the objects are.

2Compositional scenes
picture = Σ_k mask_k(slot_k, x) · decode_k(slot_k, x) for each dot x; every slot learns a coverage map (is this dot mine?) and a painting (what color is it?)
Here the picture is rebuilt as a sum, one contribution per slot. Each slot answers two separate questions about every dot: 'is this dot mine?' — a coverage map giving how likely the dot belongs to this slot — and 'what color is it?' — the slot's painted guess. Splitting the job into those two parts, which dots and what they look like, is what makes a scene with several objects easy to pull apart and reassemble: change one object and the rest are left untouched.

3Matching a word to the right object
each word is a list of numbers c; each slot is a list of numbers s_k; learn a translation W so that W·s_k lands near c only when the word truly describes that object (close for correct pairs, far for wrong ones)
The question here is: which object does a phrase like 'the red cup' point at? Words are stored as their own lists of numbers, and each slot has its own list of numbers, but the two lists live in different spaces and cannot be compared directly. The fix is to learn a translation step that maps a slot's numbers into the same space as the words, trained so that a slot lands close to a word only when they genuinely match and far away otherwise. After training, a phrase can be lined up with the right object, and no one ever had to label which object is which.
4Placing objects when generating an image
each object carries two things: a list of numbers z_k for its identity and look, and a small record T_k of its position and orientation; the new image is built object by object, so moving one object changes only its own record
When a model generates a new picture, this keeps 'what an object is' separate from 'where it goes.' Each object carries two things: a list of numbers for its identity and appearance, and a small record of its position and orientation. Because position is stored on its own and fed into the generator directly, you can move one object by editing only its position record, and every other object stays exactly as it was. That separation is what lets you arrange a scene without the objects smearing into each other.
5Objects a robot can act on
the controller reads the sentence, uses the slots to pick which objects matter, then chooses an action written as how each object should move (ΔT_k — shift and turn it) rather than as motor joint angles
A robot should act on things, not on raw joint angles. So the controller first uses the sentence to pick out which objects in the scene matter — the slots answer 'which objects are these?' — and then decides what to do in terms of how each object should move: nudge this one here, turn that one there, instead of in terms of motor angles. Because the scene has already been broken into separate objects, connecting the words in the command to the object they refer to is straightforward.
6Building the map out of objects
map = a list of objects, each with its position and orientation, a name, and a stored 3D model; each new sighting nudges that object's recorded position toward the fresh view; returning to a known place is recognized by matching object descriptions
Instead of building a map out of millions of raw 3D points, build it out of objects. The map is just a list of objects, each holding its position and orientation, a name, and a stored 3D model of its shape. As the robot moves and sees an object again, it gently nudges that object's recorded position so it agrees with the new view. When it comes back to a spot it saw earlier, it recognizes which objects are the same ones by comparing their descriptions, so the map stays consistent over time without ever having to match raw pixels.
The through-line. The core difficulty — how a dot 'knows' which object it belongs to — is really a sorting problem, and the whole method is a way to do that sorting smoothly enough to be learned. By turning each dot's match scores into shares across a few slots, the model swaps an impossible brute-force search over groupings for ordinary step-by-step improvement. Repeating the assign-then-update loop tightens the split, sending each slot toward the region it already wins. And the repaint test turns 'winning a region' from a meaningless accident into a real duty: a slot keeps a region only if it can reproduce what is there.

Two plain ideas carry the whole thing: turning scores into shares so that a choice can be learned by small nudges, and using a reproduce-the-original test as the pressure that makes those choices mean something. You will meet these same two ideas in other parts of this site. Objects appear here not because anyone defined an object, but because a small fixed set of slots, competing gently and having to repaint honestly, has nothing cheaper to do.
